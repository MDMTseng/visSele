## 2. 儀表:為什麼舊的量測看不到

改動之前,這條路徑上的所有讀數都有結構性盲點:

- **avg 對事件是瞎的**。`insp split` 在 34 萬幀上 avg 6.03ms,三分鐘的異常推不動它。
- **max 是單一 since-boot 樣本**,說不出發生頻率。
- **`WAIT SPIKE` 只在刷新最大值時才印**,所以一個早期離群值會讓之後每一次尖峰
  全部靜音。「多跑一會兒多收幾筆」是錯的。
- **`cam_max_us` 被審查**:超過預算的報告配不到物件,根本不會被計入。

所以先做儀表,再談原因:

| 儀表 | 回答什麼 | commit |

## 4. 現場

停機當下(2026-08-10 16:49),事件環第一筆:

```
e2e = 802.1ms   queue = 0.0   inspect = 16.3   wait = 761.6   write = 24.2
```

811.7ms 沒完成一次迴圈,期間只燒 0.09ms CPU。**不是沒被排到,是被擋住。**

## 5. 修正

拿掉交接,報告產生後直接寫出(`INSP_PERIF_DIRECT_SEND=1`)。
發送迴圈的 472 行(寫入 + 全部統計)抽成 `perifDeliverResult()`,兩條路徑共用同一份
程式,所以兩種模式量到的是同一組儀表。

```
                    排隊 (98k 幀)          直送 (3,098 幀 / 85s)
  wait   max        309 / 313 / 2910ms     0.0ms   (每一筆 <0.5ms)
  write  max        114 / 182 /  407ms     0.1ms   (每一筆 <0.5ms)
  e2e    max        326 / 328 / 2946ms     94.7ms
  ≥100ms 事件       18 / 14,396 幀         0 / 3,098 幀
```

### `write` 的歸因(先講錯過一次,已用量測修正)

初稿寫成「直送讓序列寫入快了一千倍」。那是錯的措辭:**鏈路速度沒有變**,而且
`write` 這個數字量的根本不是鏈路。

`write` = `sendReportTo_perifCH` 整段,拆開是兩件事:

```c
const uint64_t _lkT0 = perif_now_us();
std::unique_lock<std::mutex> _tx_guard(perif_tx_lock);   // 等鎖
const uint64_t _lkT1 = perif_now_us();
ret = perifCH->send_json_string(...);                    // 阻塞的 write()
```

第一個猜測是「等鎖」——那把鎖跟 console、WebUI 輪詢、RESET 共用,程式裡原本就
留著「140ms 是別人握著埠」的註解。**量了之後這個猜測是錯的**:

```
run23 排隊版,11,463 筆
  tx_lock   avg 0.000ms  max  0.2ms     <- 全部 <0.5ms,零競爭
  tx_wire   avg 0.137ms  max 55.9ms
  write     max 56.0ms                  <- 完全等於 tx_wire
```

`tx_wire` 也不是「上線時間」。`simple_uart_open` 之後有
`fcntl(fd, F_SETFL, 0)`,把 `O_NONBLOCK` **清掉**,所以 `write()` 是阻塞的——
它量的是**驅動收下這些 bytes 花了多久**。

機制,數量級對得上:

- mode string 是 `"8N1 none"`,`HAS_OPTION('F')` 不成立 → **硬體流量控制關閉**,
  板子無法反壓,tty 輸出緩衝一定以 230400 baud ≈ **23 KB/s** 排空
- 穩態:100 bytes × 36.5/s = 3.6 KB/s,**使用率 16%,緩衝永遠不會滿**
- 爆發:發送執行緒落後後連灌 28 筆 ≈ **2.8 KB**,超過 macOS tty 輸出緩衝(約 2KB),
  之後 `write()` 就得等它以 baud 速率排掉
- **2.8 KB ÷ 23 KB/s ≈ 122ms** — 正好落在量到的 56 / 114 / 182 / 407ms 範圍

所以結論仍然是:**當初為了保護檢驗不被寫入阻塞而加的交接,自己製造了那個會阻塞的
寫入**——但機制是「爆發把驅動緩衝灌爆」,不是「鏈路慢」,也不是「鎖被別人握著」。

### 寫入間隔下限(2ms)

因此加上 `INSP_PERIF_MIN_WRITE_GAP_US`(預設 2000)。這不只是保險,它直接對上上面
那個機制:間隔 2ms 而 100 bytes 只需約 4ms 上線,緩衝就無法累積。
36.5 報告/s 的自然間隔是約 27ms,所以**穩態下永遠不觸發**——`write_gap_naps` 會停在 0,而且它被匯出,所以這件事
可以被證明而不是被假設。它只在報告真的背靠背時作用(恢復排空、速率變更、未來的
批次呼叫者),把鏈路擋在產生 407ms 的那個區域之外。上限就是間隔本身,所以閒置的
鏈路不會累積額度、也不可能讓報告延遲超過一個間隔。

檢驗沒有變差:`inspect` avg 11.81ms(直送)對 11.55–11.67ms(排隊)。
`e2e` 的最大值現在**完全等於 `inspect` 的最大值**——剩下的是運算,不是等待。

## 8. 續章:`insp_off` 不是停滯(一整天的錯誤解讀)

修完前兩個原因後,`inspect` 階段還剩下一個未解的量:`insp_off`,定義是
**該階段的牆鐘時間減掉「檢驗執行緒自己的 CPU 時間」**,平均 3.6–4.1ms、最糟 119ms。
我整天把它讀成「執行緒被擋住了」,並據此追了四個方向。

**那個讀法是錯的。** `insp_off` 對兩件事完全無法區分:

- 執行緒被擋住(等鎖、缺頁、被搶)
- **工作正在別的執行緒上跑,呼叫端在等它**

兩者都不燒本執行緒的 CPU。這跟今天稍早 `self_cpu ≈ 0` 的過度宣稱是**同一個盲點**,
而我在把它寫進教訓欄之後又犯了一次。

### 殺死它的量測

`getrusage(RUSAGE_SELF)` 的 `ru_utime + ru_stime`——**整個行程**的 CPU,
對「是誰的執行緒」不敏感,所以沒有上面的盲點:

```
plate 停住、通告等待跳過、3600 幀
  match      avg  4.551ms   max 111.96ms
  match_cpu  avg  8.640ms   max 766.49ms      <- 行程 CPU
  比值 1.90                 尖峰時 766/112 = 6.8 核心
```

**比對期間行程燒掉 1.9 倍於牆鐘的 CPU。工作確實在跑,只是不在呼叫端執行緒上。
沒有東西被擋住。**

這一次收斂了先前所有對不上的觀察:`nivcsw = 0`(沒被搶,是在等自己派出的工作)、
優先權修正無效(worker 不受影響)、`eng_lock max 0.0`(不是鎖)、
盤子停住後 `insp_off` 反而略升(與機器無關)、
以及 `latency_stages` rig 只有 0.04ms(它是單執行緒 spin,沒有平行工作)。

### 無效的 A/B,以及為什麼它證明不了東西

中途做過 `cv::setNumThreads(1)` 的 A/B,結果毫無差異(`match` avg 4.249 → 4.239)。
當時差點拿它當反證,但 ROI 只有 318×424,OpenCV 對這種尺寸多半不拆執行緒——
**如果那個槓桿本來就沒有作用,結果沒變化就什麼都沒證明。**
一個未經確認會生效的槓桿,是無效實驗,不是反證。

### 真正剩下的問題(性質已改變)

```
match 牆鐘  avg 4.55ms → max 111.96ms    25 倍
match CPU   avg 8.64ms → max 766.49ms    89 倍
```

不是卡住,是**某些幀的實際運算量暴增近 90 倍**。這是演算法/資料相依的問題,
整機接上後再被排隊放大(`q_insp` 堆到 9/10,後續每幀 `queue` 200–250ms),
才成為觀測到的 300ms。

**因此排程、鎖、優先權、配置器、缺頁全都不是方向。** 下一步是查
「為什麼某些幀要算這麼多」。

### 這一段新增的儀表教訓

- **牆鐘減「本執行緒 CPU」分不出「被擋」和「在別的執行緒上跑」。**
  要分辨就量**行程** CPU,它對執行緒歸屬不敏感。
- **未確認會生效的槓桿 = 無效實驗。** 沒差異不等於反證。
- **讀到 `null` 的欄位比沒有欄位更危險。** 收結果時寫死欄位清單,新加的
  `match_cpu` 被靜默丟掉,差點被讀成「行程完全沒在跑」。改成收全部。

## 10. 續章 2026-08-13:裝置端被排除,以及一個一直在說謊的儀表

上面全部的結論都停在 UART 的核心側。裝置那一端從來沒有被量過,而「輪詢造成
100ms 回饋突波」一直是活著的假設——WebUI 的輪詢迴圈註解甚至寫著核心量到
`cam_trig` 遲到 115ms。

### 10.1 裝置端:排除

韌體加了 `cam_hist`(固定邊界直方圖)和 `reset_latency_stat`(只清延遲計數器,
**不碰 `CAM_SYNC`**——`reset_running_stat` 會摧毀時鐘模型,代價是約 10 秒配不上
的報告,先前每一次用它做的 A/B 都因此無效:第二臂只可能把 max 往上推)。

35/s 虛擬物件、420 秒、8509 顆、鏈路除每 20 秒一次約 180 B 的讀取外全靜默:

```
avg 14.1ms   max 47.7ms
  10-20ms   8192   96.27%
  20-40ms    315    3.70%
  40-80ms      2    0.02%
  >=60ms       0

loop_max = 2.9ms  over 9,975,303 passes
```

**主迴圈在近千萬次 pass 中最長 2.9ms。** 裝置不會卡住。另外做過 180 秒的
quiet/polled 對照:輪詢只讓平均 +0.4ms、把約 1.6% 的顆從 10-20ms 桶推到 20-40ms

### 10.2 `data/slowframes` 的 60 個檔名不可信

存慢幀時 `sf.match_cpu_ms = g_lastMatchProcCpuUs`,而**計算 `g_lastMatchProcCpuUs`
的那段程式排在存圖之後**——所以每個檔名蓋的是**前一幀**的 CPU。列成表會看到
60 張裡 59 張是 3-13ms CPU 對 50-1594ms 牆鐘(最糟 1594ms 對 4ms),那正是
「執行緒被擋住」的特徵,和 §8 的結論正好相反,而且是假的:前一幀是正常幀,所以
全部落在 4-9ms;唯一讀到 99ms 的那張,是跟在另一張慢幀後面的慢幀。

已修(`rusnap()` 移到 match 結束後)。**聚合直方圖不受影響**——它們加在賦值之後,
所以 §8 站得住。**那 60 個檔名要重收。**
