# 報告 2026-08-10 — 報告路徑的長延遲

**問題**:每隔幾分鐘到幾十分鐘停機一次,`error_hist [1]`
(`INSP_RESULT_MATCHES_NO_OBJECT`)。等價於「某一份報告晚於 CAM→SWITCH 預算」,
freq 13000 時預算是 **792ms**。

**結論**:兩個獨立的原因,都已修。

| # | 原因 | 修正 | 效果 |
|---|---|---|---|
| 1 | `image_pipe_info_gc` 每幀漏一棵 cJSON 樹 | `635865bc` | 92MB/分鐘 → 持平 |
| 2 | 報告經 `perifSendQueue` 交接,消費者喚醒晚 175–2910ms | `2b3649b2` | `e2e` max 326 → 94.7ms |

原因 1 的完整過程在 `POSTMORTEM_2026-08-10_stall.md`。本文是原因 2。

## 1. 為什麼原因 1 修掉之後還會停機

修掉洩漏後 footprint 45 分鐘持平,停機間隔也不再單調縮短——但仍然停機
(run 13:8.3 / 3.6 / 27.5 分鐘)。決定性的事實:

> `cam_max_us = 598188`(598ms)出現在**第 3.6 分鐘**,當時 footprint 才 40MB,
> 完全沒有壓縮或交換。

**在乾淨的記憶體狀態下就已經有 600ms 級的延遲。** 洩漏只是把它放大過預算。

## 2. 儀表:為什麼舊的量測看不到

改動之前,這條路徑上的所有讀數都有結構性盲點:

- **avg 對事件是瞎的**。`insp split` 在 34 萬幀上 avg 6.03ms,三分鐘的異常推不動它。
- **max 是單一 since-boot 樣本**,說不出發生頻率。
- **`WAIT SPIKE` 只在刷新最大值時才印**,所以一個早期離群值會讓之後每一次尖峰
  全部靜音。「多跑一會兒多收幾筆」是錯的。
- **`cam_max_us` 被審查**:超過預算的報告配不到物件,根本不會被計入。

所以先做儀表,再談原因:

| 儀表 | 回答什麼 | commit |
|---|---|---|
| 五段直方圖 `queue/inspect/wait/write/e2e` | 尾巴長在哪一段 | `bd564b62` |
| watchdog(2ms 週期、無鎖無 I/O、同 QoS) | 是整台機器停,還是單一執行緒沒被排到 | `08be16b5` |
| 五條執行緒心跳 | 一條停,還是全部停 | `08be16b5` |
| 事件環(32 格,GS 讀出) | 每筆 ≥100ms 的完整現場 | `08be16b5` |
| `log` 直方圖 | 送出執行緒自己的日誌是不是元兇 | `b257dfc3` |
| `parked_before_enq_ms` | 已經在等卻沒被叫醒,還是根本還沒走到 pop | `43c45225` |
| harness 的 `host{load1,core_pct,other_pct}` | 這筆數字有沒有被主機負載汙染 | soak5h.py |

桶邊界刻意跨過死線(…400 / 600 / **800** / 1200),所以 **≥800ms 那一桶的數量,
本身就是來不及判定的顆數**。

## 4. 現場

停機當下(2026-08-10 16:49),事件環第一筆:

```
e2e = 802.1ms   queue = 0.0   inspect = 16.3   wait = 761.6   write = 24.2
age: send 811.7 | dview 0.9 | rx 1.1 | insp 1.1 | dog 15.8
self_cpu = 0.09ms    q_send = 28
```

預覽、取像、檢驗全部 <1.2ms 新鮮;同 QoS 的 watchdog 15.8ms;而送出執行緒
811.7ms 沒完成一次迴圈,期間只燒 0.09ms CPU。**不是沒被排到,是被擋住。**

重複出現的形狀(run 17):

```
e2e=328.0 wait=313.9 | send=343.7  dview=343.8  rx=5.8  insp=5.8  dog=0.2
e2e=149.6 wait=137.3 | send=165.5  dview=165.5  rx=15.4 insp=15.4 dog=93.9
e2e=110.3 wait= 99.2 | send=126.0  dview=126.0  rx=2.2  insp=2.2  dog=2.2
```

**送出與預覽每次凍住的時間一致到 0.1ms。** 它們不共用佇列也不共用鎖。唯一的共同點
是**它們是僅有的兩條停在 `pop_blocking`(條件變數)上的執行緒**;在跑的執行緒和睡在
計時器上的 watchdog 都不受影響。

`parked_before_enq_ms` 收尾:

```
e2e=199.0  wait=175.6  PARKED=+35.3 | send=211.2 dview=211.2 dog=0.4 nivcsw=0
```

正值代表**東西進佇列前 35.3ms,執行緒就已經停在 pop 裡等**,然後花 175.6ms 才醒,
而當下沒有任何非自願上下文切換。**東西已入列、notify 已發出,消費者晚了 175ms。**

## 5. 修正

拿掉交接,報告產生後直接寫出(`INSP_PERIF_DIRECT_SEND=1`)。
發送迴圈的 472 行(寫入 + 全部統計)抽成 `perifDeliverResult()`,兩條路徑共用同一份
程式,所以兩種模式量到的是同一組儀表。

```
                    排隊 (98k 幀)          直送 (3,098 幀 / 85s)
  wait   max        309 / 313 / 2910ms     0.0ms   (每一筆 <0.5ms)
  write  max        114 / 182 /  407ms     0.1ms   (每一筆 <0.5ms)
  e2e    max        326 / 328 / 2946ms     94.7ms
  ≥100ms 事件       18 / 14,396 幀         0 / 3,098 幀
```

### `write` 的歸因(先講錯過一次,已用量測修正)

初稿寫成「直送讓序列寫入快了一千倍」。那是錯的措辭:**鏈路速度沒有變**,而且
`write` 這個數字量的根本不是鏈路。

`write` = `sendReportTo_perifCH` 整段,拆開是兩件事:

```c
const uint64_t _lkT0 = perif_now_us();
std::unique_lock<std::mutex> _tx_guard(perif_tx_lock);   // 等鎖
const uint64_t _lkT1 = perif_now_us();
ret = perifCH->send_json_string(...);                    // 阻塞的 write()
```

第一個猜測是「等鎖」——那把鎖跟 console、WebUI 輪詢、RESET 共用,程式裡原本就
留著「140ms 是別人握著埠」的註解。**量了之後這個猜測是錯的**:

```
run23 排隊版,11,463 筆
  tx_lock   avg 0.000ms  max  0.2ms     <- 全部 <0.5ms,零競爭
  tx_wire   avg 0.137ms  max 55.9ms
  write     max 56.0ms                  <- 完全等於 tx_wire
```

`tx_wire` 也不是「上線時間」。`simple_uart_open` 之後有
`fcntl(fd, F_SETFL, 0)`,把 `O_NONBLOCK` **清掉**,所以 `write()` 是阻塞的——
它量的是**驅動收下這些 bytes 花了多久**。

機制,數量級對得上:

- mode string 是 `"8N1 none"`,`HAS_OPTION('F')` 不成立 → **硬體流量控制關閉**,
  板子無法反壓,tty 輸出緩衝一定以 230400 baud ≈ **23 KB/s** 排空
- 穩態:100 bytes × 36.5/s = 3.6 KB/s,**使用率 16%,緩衝永遠不會滿**
- 爆發:發送執行緒落後後連灌 28 筆 ≈ **2.8 KB**,超過 macOS tty 輸出緩衝(約 2KB),
  之後 `write()` 就得等它以 baud 速率排掉
- **2.8 KB ÷ 23 KB/s ≈ 122ms** — 正好落在量到的 56 / 114 / 182 / 407ms 範圍

所以結論仍然是:**當初為了保護檢驗不被寫入阻塞而加的交接,自己製造了那個會阻塞的
寫入**——但機制是「爆發把驅動緩衝灌爆」,不是「鏈路慢」,也不是「鎖被別人握著」。

### 寫入間隔下限(2ms)

因此加上 `INSP_PERIF_MIN_WRITE_GAP_US`(預設 2000)。這不只是保險,它直接對上上面
那個機制:間隔 2ms 而 100 bytes 只需約 4ms 上線,緩衝就無法累積。
36.5 報告/s 的自然間隔是約 27ms,所以**穩態下永遠不觸發**——`write_gap_naps` 會停在 0,而且它被匯出,所以這件事
可以被證明而不是被假設。它只在報告真的背靠背時作用(恢復排空、速率變更、未來的
批次呼叫者),把鏈路擋在產生 407ms 的那個區域之外。上限就是間隔本身,所以閒置的
鏈路不會累積額度、也不可能讓報告延遲超過一個間隔。

檢驗沒有變差:`inspect` avg 11.81ms(直送)對 11.55–11.67ms(排隊)。
`e2e` 的最大值現在**完全等於 `inspect` 的最大值**——剩下的是運算,不是等待。

## 6. 尚未證明

- **85 秒不足以宣告停機消失。** 5 小時驗證跑(run 22)進行中。
- **高負載下的寫入**沒有重測。直送讓寫入不再爆發,但驅動本身仍可能停滯。
  run23 在乾淨窗口量到 `tx_wire` max 55.9ms,而 run19(遠端桌面 + 主機被我佔用)
  量到 407ms——同一個機制在髒環境下更嚴重,但沒有做對照實驗。
- **`dog max 132–2379ms` 仍然存在**,那條路徑沒被這次改動碰到,也與報告無關;
  它是否為 `nanosleep` 的計時器假象尚未分離。
- **`setThreadPriority` 有真缺陷,未修**:傳的是 nice 值域(-20..19)而 `SCHED_RR`
  在此機器是 15..47,`-20` 直接 EINVAL 失敗且**錯誤被吞掉**(印錯誤那行被註解);
  結果是檢驗執行緒的優先權從未設成功,而**存 NG 圖的執行緒(RR 19)排在報告路徑
  (RR 10)之上**。`FI_INSP_NG_SNAP` 是 true,所以它真的會跑。
- **`log_dump` 在停機當下 60 秒交不出檔案**,且 run 17 以
  `console silent for 3 samples` 中止。日誌/console 子系統另有問題。

## 7. 這次的儀表教訓

- **`ps -o rss` 在 macOS 不計壓縮頁**;用 `footprint -p`。(原因 1 的最貴錯誤)
- **佇列滿 ≠ 消費者忙**,而是消費者落後。
- **`self_cpu ≈ 0` 不能區分「被餓死」和「等鎖」**,兩者都不燒 CPU。
- **`virt_drop` 是停機的結果不是原因**,它等於 `rej_blocked`,是機器自己關閘。
- **量測主機的負載必須跟每一筆樣本一起記**,否則尾巴數字事後無法歸因。
- **會過期的證據不算證據**:log ring 約 5 分鐘,run 13 的三次停機全部在收尾前消失;
  事件環改成記憶體常駐才拿到現場。
