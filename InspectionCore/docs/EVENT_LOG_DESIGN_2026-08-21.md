# 事件記錄設計 — 什麼值得寫,為了回溯什麼問題

2026-08-21。這是一份設計提案,不是已完成的實作。

出發點不是「有哪些變數可以存」,而是**今天實際卡住的每一次,當下缺的是什麼**。
每一個欄位下面都掛著一個它要回答的問題;回答不了任何問題的欄位不要寫,因為
記錄的成本從來不是磁碟,是**寫太多之後沒有人找得到重點**。

---

## 0. 先講三個原則,它們決定了其他所有決定

### 記錄「轉變」,不是「取樣」

每分鐘存一次狀態,會同時做到兩件壞事:產生大量重複資料,又照樣漏掉毫秒級的
事件。`g_perifTxFail` 從 3 變成 4 的那一刻才是事件;它維持 4 的那三個小時不是。

反過來說,**低頻的心跳仍然需要**,理由不是記錄狀態,是給事件提供「之前正常」的
對照。沒有對照的話,一筆孤立的錯誤永遠可以被解釋成「本來就這樣」。

### 分子沒有分母就沒有意義

「掉了 47353 件」是個嚇人的數字,直到你知道同期看到了 210576 件。今天
`yield` 漏斗之所以能一眼指出問題,就是因為它每一關都有進、出、和具名的流失
原因。**任何丟棄計數都必須和同期的嘗試次數寫在同一筆記錄裡**,否則事後要靠
兩個不同時間點的快照去湊,而那正是誤差的來源。

### 「沒有回答」和「回答了壞消息」必須分得開

這是今天重複最多次的失敗模式,而且每一次都指向硬體:

- `{"err":"no perif channel"}` 沒有 `id`,`ask()` 回 `null`,而
  `if (st && st.state !== 112)` 對 `null` 也是 false ——「板子沒回應」被報成
  「板子卡在 112」。
- 今晚 `read ECONNRESET` 被報成 `board not answering`,實際上是 socket 死了,
  板子好得很。
- 兩次 soak 失敗都被記成「板子沒回應」,真正的原因是核心的 COM3 關掉後沒再打開。

所以事件的類型必須把 **timeout / 連線層失敗 / 對方明確回報錯誤** 分成三種,
永遠不要合併成一個 `error`。

## 1. 今天缺過的資訊,逐條列

這一節是整份設計的證據。左邊是當時想問的問題,右邊是為什麼答不出來。

| 當時的問題 | 為什麼答不出來 |
|---|---|
| 板子的 `err [12]` 是什麼時候發生的? | `error_hist` 的元素是**裸錯誤碼**(`Diagnostics.hpp:42`),沒有時戳 |
| `unans` 從 0 變成 1 是哪一顆料件、什麼時候? | 只有累計計數,沒有事件 |
| `cal_lost 55` 是集中在某一分鐘,還是九小時均勻散布? | 同上。這兩者是完全不同的機器狀態 |
| COM3 關掉之後為什麼沒再打開? | 只有核心 stdout 看得到,而生產環境 `persist OFF`,log 只在 RAM ring |
| 那次 215 ms 的 `write()` 阻塞,和 `UNANSWERED` 跳到 31 是同一件事嗎? | 兩個數字在不同地方、不同時間軸,只能用推論串 |
| 上一輪跑的時候淨空區擋掉幾成? | 沒有任何持久化記錄 |
| 這次故障之前,機台跑了多久、多少件、什麼速度? | 沒有 session 概念,計數器只有「自行程啟動以來」 |

**共同點:每一個都是「時間」或「當下的上下文」的問題,而不是「數量」的問題。**

## 2. 三層結構

分層的目的是讓**高頻的東西便宜、低頻的東西詳細**,而不是所有東西都寫一樣多。

```
 L1 事件   轉變發生時寫一筆        高價值、低頻     永久保留(輪替)
 L2 心跳   每 60 s 一筆            提供對照基線     保留數天
 L3 現場   L1 觸發時附帶的大包     昂貴、罕見       保留最近 N 次
```

---

## 3. L1:事件 — 每一筆都要有的共同表頭

```json
{"t_wall":"2026-08-21T20:29:41.372+08:00",
 "t_mono_us":41287193,
 "board_uptime_s":33869,
 "cam_offset_us":42121527910,
 "seq":10482,
 "sev":"error",
 "ev":"perif_tx_fail",
 ...}
```

**四個時間基準,少一個都會斷線索:**

- `t_wall` —— 人看的,也是唯一能跟操作員說「你說的那個時候」對上的東西。
- `t_mono_us` —— 單調時鐘。牆鐘會被 NTP 校正甚至倒退,排序不能靠它。
- `board_uptime_s` —— 板子自己的時間軸。板子重開機會歸零,所以**它不能單獨用**,
  但它是唯一能對上板子 ISR 事件的量。
- `cam_offset_us` —— 相機時戳域的偏移。這是把主機時間和板子時間**接起來的橋**;
  沒有它,「報告延遲 262 ms」和「那一刻主機在做什麼」永遠對不起來。

`seq` 單調遞增,用來偵測記錄本身有沒有掉。**記錄系統必須能證明自己沒漏**,否則
「沒有事件」和「事件沒被寫下來」無法區分 —— 這跟核心裡那句
「無聲丟棄與無聲停滯從外面看一模一樣」是同一個道理。

`sev` 分 `info` / `warn` / `error` / `fatal`,讓事後可以先只看 error 以上。

## 4. L1:該記哪些事件

### 4.1 周邊連線(對應 `wiringPanel.cpp:230-239`)

```json
{"ev":"perif_link","state":"down","reason":"tx_fail",
 "ctx":{"consec":3,"tx_fail_total":47,"queue_dropped":0,
        "no_channel_drop":12,"sent_since_up":18422,"up_duration_s":3617}}
```

- `state`: `up` / `down` / `suspect`。目前 `g_perifLinkSuspect` 是個布林閂鎖,
  「曾經斷過」只留下一個 true —— 這裡要的是每一次轉變各一筆。
- `reason` 必須分開:`tx_fail`(寫入失敗)/ `no_channel`(通道不存在)/
  `timeout`(送出了但沒回)/ `closed`(對方關閉)。第 0 節講的三分法。
- `sent_since_up` 是**分母**。47 次失敗在 18422 次送出裡,和在 200 次裡,不是
  同一台機器。
- `up_duration_s` 回答「它撐了多久才斷」,這是判斷「開機就壞」還是「跑久了才壞」
  的關鍵,而今天的資料完全無法區分這兩者。

### 4.2 序列埠生命週期 —— 今晚就是死在這裡

```json
{"ev":"uart","action":"close","port":"COM3","baud":230400,
 "ctx":{"open_count":6,"total_open_s":18244,"reopen_after_ms":null,
        "caller":"perif_channel_release"}}
```

`open_count` 累積到 6 之後就沒有再 open,而核心還活著、埠還在 listening。
**`reopen_after_ms` 是 null 這件事本身就是答案** —— 如果有這筆記錄,今晚就不用
花時間去猜是板子壞了還是核心壞了。`caller` 說明是誰要求關的,這決定了是誰的
生命週期管理有問題。

### 4.3 板子錯誤(對應 `Diagnostics.hpp:42`、`SyncTask.cpp:991`)

因為韌體的錯誤碼**不帶時戳**,核心只能在**發現差異的當下**蓋章:

```json
{"ev":"board_error","codes_new":[12],"codes_all":[12],
 "detected_by":"poll_diff","poll_gap_ms":1000,
 "ctx":{"state":112,"prev_state":101,"rpm":17.0,"uptime_s":33869}}
```

- `detected_by` + `poll_gap_ms` 誠實表達**時間精度**:這筆的時間誤差最大就是輪詢
  間隔。假裝它是精確時刻是在說謊,而事後有人會拿它去對 ISR 事件。
- **`clear_error_history` 之前必須先寫一筆 `board_error_snapshot`。** 今天每次
  bring-up 都呼叫它,所以「跑之前板子是 112 err[12]」只存在於我的終端輸出裡,
  機台自己什麼都沒留。清除是破壞性動作,破壞前落地是這個 FR 最直接的價值。

### 4.4 板子狀態轉換

```json
{"ev":"board_state","from":101,"to":112,
 "ctx":{"error_hist":[12],"in_state_s":1843,"parts_in_state":42117}}
```

`in_state_s` 和 `parts_in_state` 讓「跑了半小時才壞」和「一啟動就壞」在資料上
長得不一樣。

### 4.5 判定與料件遺失(對應 `:243`、`:248`、`:249`、`:425-432`)

```json
{"ev":"verdict_lost","reason":"unanswered","n":1,
 "ctx":{"since_last_s":1841,"admitted_since":41203,
        "insp_wall_ms":13.1,"queue_depth":3,"lat_cam_us":31616}}
```

- `reason` 直接沿用既有的八個分類(`g_naNoObject`、`g_naMultiObject` …),不要
  重新發明一套。
- `since_last_s` 把「偶發」和「連發」分開,這是今天 `cal_lost 55` 無法回答的
  那個問題。
- **`insp_wall_ms` 和 `queue_depth` 是關鍵**:遺失的當下引擎在忙嗎?這一欄直接
  決定了要往「引擎太慢」還是「連線問題」查。

### 4.6 延遲尾巴(對應 `wiringPanel.cpp:3983` 的 `lat_events` 環)

目前是 32 筆的 RAM 環,重啟就沒。超過門檻的那幾筆應該落地:

```json
{"ev":"lat_spike","e2e_ms":215.3,
 "phase":{"queue":0.1,"inspect":13.2,"wait":0.6,"write":201.4},
 "ctx":{"budget_ms":1029,"used_pct":20.9,"unans_total":31}}
```

**分項是重點,不是總和。** `MACHINE_FLOW.md` 那次之所以能定位到
「`write()` 被阻塞、不是頻寬問題」,靠的就是這個拆解。`budget_ms` 一起寫是為了
讓這筆記錄**自己就能判讀**,不需要讀的人記得公式
`(29900-9315)/(2×plate_freq)` —— 而那個公式今天被算錯過兩次。

### 4.7 時戳配對健康

```json
{"ev":"camsync","kind":"resid_grow","resid_us":-4,"resid_max_us":-5,
 "delta_max_us":3,"window_us":5000,"rejected":0,"drift_us_per_s":-47.6}
```

只在**跨越比例門檻**時寫(例如 `|resid| > window/10`),不要每幀寫。理由在
soak 的註解裡:殘差變大 → 配對靠近窗邊 → 誤配 → **一個零件被另一個零件的影像
判定**,而這是這台機器最糟的失效模式,因為它從外面看完全不像錯誤。

### 4.8 設定變更 —— 這一類最容易被忘記,但回溯時最常需要

```json
{"ev":"config","key":"clean_regions","from":2,"to":0,
 "source":"ST:MachineSetting","persisted":false,"peer":"127.0.0.1:52193"}
```

今天有大量的執行期變更(`clean_regions`、`dark_thresh`、`min_detect_sep_us`、
`plate freq`),全部只存在於我的腳本輸出。**`persisted` 這一欄特別重要**:區分
「改了 RAM」和「寫進 NVS/檔案」,否則事後看到行為改變卻找不到對應的檔案差異,
會往完全錯的方向查。

## 5. L2:心跳 — 提供對照,不是提供狀態

每 60 秒一筆,欄位就是今晚 soak 在用的那組,因為它們已經被證明夠用:

```
t_wall, seq, state, seen_s, admit_s, sorted_s, na_s,
skip, unans, lat_avg_ms, lat_max_ms, lat_tail_n,
resid_us, delta_max_us, window_us,
core_rss_mb, core_cpu_pct, insp_wall_ms_avg, queue_depth_max
```

加了 `core_cpu_pct` 和 `queue_depth_max`,今晚量到核心是 122% of one core,
而從 `insp_wall_ms` 推算只有 28% —— 差距來自影像編碼和多執行緒定位。**這個差距
本身就是一個值得長期追蹤的量**,如果哪天它變了,代表有東西在背景多做了事。

心跳的價值只有一個:當 L1 寫下一筆錯誤時,能回頭看前 10 分鐘是不是已經有徵兆。
沒有基線的異常值無法判讀。

## 6. L3:現場快照 — 只在真的壞掉時

`sev >= error` 時附帶一包大的,存成獨立檔案並在 L1 事件裡引用檔名:

- 完整的 `get_running_stat` 與 `get_setup`(板子的全部狀態與設定)
- 核心那 20 幾個計數器的完整快照
- `lat_events` 整個 32 筆的環
- log ring 的最後 N 筆(核心已經有 `log_dump` 機制,直接複用)
- 當下那一幀的影像與報告 JSON(如果還在)

保留最近 N 次即可。這一層昂貴,所以罕見才划算。

---

## 7. 明確不要寫的東西

同樣重要,因為寫太多會讓這套系統變成第二個沒人看的 log:

- **不要每幀寫。** 23 幀/秒 × 六小時 = 50 萬筆,重點會被埋掉。
- **不要寫「一切正常」的事件。** 那是 L2 心跳的工作。
- **不要寫已經能從別處算出來的衍生值**,除非它是為了讓記錄自己可判讀
  (`budget_ms` 是刻意的例外)。
- **不要寫影像進 L1/L2。** 影像進 L3,而且要有數量上限 —— 這台已經有
  `save_snap_disk_low_skip_count`(`wiringPanel.cpp:152`),磁碟壓力是真實的。

## 8. 為「有人盯著看」設計的量測,在無人長跑時會失效

這是一整類問題,不是單一缺陷。2026-08-22 在 soak 裡撞到之後才看清楚。

### 症狀:殘差包絡

`cam_sync.resid_max_us` 是**會衰減的包絡**(`LegacyFirmware.cpp:704`):

```cpp
if(llabs(last_resid_us) > llabs(max_resid_us)) max_resid_us = last_resid_us;
else if(max_resid_us != 0) { int64_t m = llabs(max_resid_us);
                             m = m - (m / 1000) - 1; ... }
```

每個樣本**至少扣 1 µs**,而穩態是 23.3 幀/秒:

```
峰值    7 us  ->  0.3 秒歸零
峰值  100 us  ->  4.3 秒
峰值 1047 us  -> 43.9 秒
峰值 5000 us  -> 97.9 秒(整個窗)
```

soak 每 **60 秒**取樣一次。**除非峰值發生在取樣前的零點幾秒內,否則永遠看不到。**
六小時 soak 讀到的「殘差最大 7 µs」,實際意義是「最近 0.3 秒的活動水準」,不是
「這段期間最糟」。連 1047 µs 等級的事件都會在下一次取樣前完全抹平。

這直接影響了一個已經寫下的結論:第一輪 soak 那 74 顆 SKIP,我當時說「跟時戳無關」。
`ts_rej = 0` 仍然成立(那是真正的累計計數),但**殘差的部分只能說「沒有觀察到」,
不能說「沒有異常」** —— 事件持續約 3 秒,下一次取樣在 54 秒後。

### 這台機器上同一類的量測

| 量測 | 遺忘方式 |
|---|---|
| `cam_sync.resid_max_us` | 每樣本衰減,0.3–98 秒歸零 |
| 韌體 `error_hist` | 環形緩衝,**元素不帶時戳**,`clear_error_history` 整個抹掉 |
| 核心 `lat_events` | 只有 32 筆,被後續事件覆蓋 |
| log ring | `persist OFF` 時只在 RAM |

### 設計原則

**任何會自己遺忘的量測,都必須同時提供一個不會遺忘的版本。** 否則長跑量到的是
「取樣當下」,而不是「這段期間」—— 而長跑存在的唯一理由就是後者。

### 做法:查詢時 opt-in 重置

```json
{"type":"get_running_stat", "reset_stat_maximum": true}
```

不帶旗標 = 今天的行為,所以**被動讀取者不受影響** —— WebUI 只是要顯示,不帶旗標,
就不會干擾任何人。這是關鍵:危險的從來不是 read-and-clear,是**隱含的**
read-and-clear。做成 opt-in 之後,清除是呼叫者明確要求的行為。

也比「讀取後再送一個 reset」好,因為那兩步之間有一個空窗,落在裡面的峰值會消失。

**衰減必須同時拿掉。** 只加 reset 不解決問題 —— 衰減發生在兩次查詢**之間**:

```
t+0s    poll(reset:true)  -> 歸零
t+1s    出現 7 us 峰值
t+1.3s  衰減吃掉它        -> 回到 0
t+60s   poll(reset:true)  -> 讀到 0     還是漏掉
```

而且一旦有了 reset,**衰減本來就沒有存在的必要**。衰減是為了「沒有辦法清除」而
發明的近似;有了 per-request reset,每個讀取者拿到的是「距離你上次讀取以來的
最大值」—— 對每秒盯著看的操作員,那是「最近 1 秒的最大值」,比包絡更準確也更好
解釋。這是用更好的機制取代一個 workaround,不是多加一個模式。

### 三個實作上的約束

**1. 絕對不能碰累計計數。** 名字已經說對了(maximum),但要寫死在實作裡:
`skip`、`unans`、`tx_fail`、`gate.loss_n` 這些必須**跨 reset 存活**,否則 soak 每
分鐘 poll 一次就會洗掉自己的累計基準,而「74 顆 SKIP 之後 364 分鐘沒再增加」這種
判讀就永遠做不出來。既有的 `reset_running_stat` 是粗粒度的、連計數一起清,新旗標
必須嚴格只清 maxima。

**2. 一併回傳這個 max 涵蓋多長的區間**(例如 `stat_max_window_ms`)。殘留風險是
**兩個讀取者都帶 `reset:true` 會互相偷峰值**,而這台真的有多個讀取者(WebUI、
bench 工具、`board_rescue`)。回傳區間長度之後,讀取者能發現「我要 60 秒的最大值,
拿到的只涵蓋 1.2 秒」,而不是默默把它當成 60 秒的結果。

這正是第 0 節那條原則的延伸:**量測必須能證明自己涵蓋了什麼**,否則「沒有峰值」
和「峰值被別人拿走了」無法區分。

**3. 一致地套用到所有 `_max_` 欄位**,不要只做 `resid`。`isr_dur_max_us`、
`cam1_pw_err_max_us`、`REP_LAT_MAX_US`、gate 的各種 max —— 同一個旗標、同一套
語意。否則下次又要為另一個欄位重想一遍,而讀的人得記住哪些會 reset 哪些不會。

順帶一提,韌體本來就有 `_env_` / `_max_` 並存的慣例
(`LegacyFirmware.cpp:6252-6275`,ISR 時間和相機脈寬都是),只有 `cam_sync` 沒跟上。
改成 reset 語意之後,`_env_` 那一半可以一併退場。


## 9. 格式、位置、輪替

- **JSONL**(一行一筆),append-only。壞掉的一行不會毀掉整個檔案,這對「當機前
  最後一筆」特別重要 —— 而那一筆往往就是最有價值的一筆。
- 位置在 `data/events/`,依日期切檔;單檔上限 + 保留 N 天。
- **落地策略要選:** 每筆 `fflush` 最安全但最慢;純緩衝最快但當機時會丟掉最後
  幾筆,而那正是要的幾筆。建議 **`sev >= warn` 立刻 flush,`info` 走緩衝**。
- **寫入必須不阻塞檢驗執行緒。** 這台的節拍是 54 ms(或 10000 轉速下 43 ms),
  一次同步寫檔可能吃掉整個預算。應該進一個有界佇列由獨立執行緒寫出 —— 而且
  **佇列滿了要有 `events_dropped` 計數並在恢復時寫一筆**,否則這套系統自己就會
  犯它要解決的那個毛病。
