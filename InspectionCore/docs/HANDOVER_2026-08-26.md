## The three folders, and which one bites

The launcher now has three configured paths, and the difference between them is
the single most important thing in this file.

| | What it is | The launcher... |
|---|---|---|
| `appRoot` | versions + `current.json` | **deletes from it** (prune, and install replacing a version) |
| `workingDir` | the machine's identity — `data/`, calibration, recipes | only passes it to the core. Never creates, copies, moves or deletes |
| `updateSource` | where packages arrive: `data/sync/DEV/<機種>/update` | **reads only, forever** |

**`updateSource` lives INSIDE `workingDir`.** That is the normal fleet layout,
not a mistake. The containment check is therefore **one-directional**: only
`appRoot` containing something else is dangerous, because `appRoot` is the only
path anything is ever deleted from. A "these three must not overlap" check would
reject the real installation, and a check that blocks a correct setup teaches
operators to ignore checks.

**Nothing may ever delete inside the sync share.** A deletion there does not stay
there; it reaches all fifteen machines. This is why `install()` only reads, and
why the e2e test asserts the folder is byte-for-byte unchanged afterwards.

## Getting back into the launcher

Once the application's UI takes the window, every settings action is refused
(`assertShell`). There is no menu and no keyboard shortcut, and these are
touch-only machines.

**Three taps on the splash screen.** The countdown is on screen while the core
boots; three taps within 900 ms of each other stop the start and keep the
launcher up. `splashHoldMs` (default 3000) is a **floor**, not a delay — the
core is spawned first, so on a normal boot the taps overlap with a startup that
was happening anyway and cost nothing. Set it to 0 to close the gate entirely.

A stop the launcher asked for is reported as **設定模式**, not as a crash.

`tools/gate_smoke.mjs` proves both halves: left alone the app UI takes the
window; tapped three times it does not.

## Update and rollback

**Install and switch are separate, and that is what makes all of this safe.**
Installing only writes a new directory under `appRoot` — `install()` refuses to
replace the selected version, and never touches `workingDir`. Selecting is one
small write to `current.json`, which is read at start and never again. So both
can happen while the machine inspects, and neither disturbs the run in progress.

That is why there is **no unattended switch**. The operator is told, and picks
the restart moment.

```
company drops a zip + edits release.json   →  Resilio syncs to 15 machines
the machine says "有新版本 1.1.104"        →  operator installs (production continues)
operator picks a moment, restarts          →  new version runs
it does not work                           →  three taps → the 已驗證 row → 設為現行
```

**`release.json` is a pointer, not "newest wins".**

```json
{ "version": "1.1.104" }
```

Newest-wins cannot express a rollback: roll a machine back and the next scan
offers the bad version again, forever. With a pointer, going back is editing one
field — and the package is already on disk, so nothing is downloaded. `DEV` and
`<機種>` are already in the path, so channels and per-model staging come free;
no separate channel file is needed.

**Last known good is earned by RUNNING, not by starting.** `goodAfterMs` is
three hours — a real production stretch. "It started" is no evidence at all; a
build that dies after ten minutes starts perfectly. The record is written when
the timer fires, never at shutdown, so a machine that crashes still accumulates
one and a machine that is killed cannot claim a stretch it did not finish.

A machine restarted more often than three hours would never earn one, so
`current.json` also remembers what it displaced. **prune protects both**,
regardless of `keepVersions`. This mattered: measured on the pre-change code
with `keepVersions=3`, five updates deleted the proved version.

Both are tagged in the version table — **已驗證** with how long it ran, and
**前一版** — because an operator choosing a rollback target under pressure
should not have to guess.

## Contracts added today

To the two in the previous handover (`extra`, `quality_essential`), add:

- **The sync share is read-only to the launcher.** Any future feature that
  tidies, prunes or rewrites anything under `updateSource` is wrong, however
  local it looks.
- **`appRoot` is the only path anything deletes from.** Keep it that way; it is
  what makes the one-directional containment check sufficient.
- **The WebUI must work with no launcher at all.** It runs in a plain browser
  against the Vite dev server and under launchers older than any given IPC. Gate
  every `window.launcher.*` call on its own existence, and disable the feature
  permanently on the first failure rather than retrying. `tools/webui_failsafe.mjs`
  enforces this for the update notice; extend it for the next such feature.
- **A version directory may not start with a dot.** Dot-directories are launcher
  machinery (`.staging`, `.replaced`) and `list()` hides them.

## Caveats added today

- **A file listing from the sync share contains things that are not files you
  want.** `name.includes(".hydef")` matched `x.hydef.!sync` (a partial download),
  `x.Conflict.2026-08-26.hydef` (another machine's copy) and let `.sync/` and
  `.SyncArchive/` be browsed. All three look like a working recipe in the
  picker. Use the shared filters in `UTIL/BPG_Protocol.js`
  (`defFileFilter` / `makeExtensionFilter` / `isSyncArtifact`) rather than
  open-coding an extension test — there were five copies of that test.
- **A zip is only complete when no `.!sync` sibling remains.** The updater's
  scan enforces this; anything else reading that folder must too.
- **Node emits `'error'` and NO `'exit'` when a process can never be spawned.**
  A missing exe therefore left the supervisor believing the core was running,
  forever. Any new process wired into the supervisor needs the same treatment.
- **Rollback does not cover data.** `data/` is machine identity and is not
  versioned, so a release that migrates `machine_setting.json` or a def and
  writes it back cannot be cleanly rolled back. Such releases must be marked.
- **The core does not verify the def's `featureSet_sha1`; the WebUI does, and
  that is the right place.** `LD` only reads the file's bytes and ships them to
  the UI as `FL`; the UI verifies and then sends `definfo` back. **The UI is
  upstream of the core** — a def that fails integrity never reaches it.
  Reimplementing JSum in C++ would need bit-exact JavaScript number formatting
  on cJSON doubles, and getting it wrong refuses every def. Do not.

## What is left

`BACKLOG_2026-08-26.md`, ordered by what it costs if it stays broken. The two
that matter most:

- **B6** — `edge.min_strength=0` is editable on screen and the core substitutes
  10 (also `blur`→3, `mask_dilate`→8, `include_range`→2 px). **`test1.hydef`
  sits on these hidden substitutions right now**, so the recipe in production is
  not the recipe on screen.
- **U4** — recipes are shared company-wide on a **bidirectional** sync, so an
  operator pressing save changes all fifteen machines, with no review and no
  staging. This is the one risk in the fleet design with no mitigation at all,
  and it needs a decision rather than a fix. Options: local save plus an
  explicit publish; a read-only sync folder with editing elsewhere; or at
  minimum a UI warning saying what save actually does.

Also still open: firmware F1/F2 (two memory corruptions, on the board that
drives the air valves) and F3 (the SEL valve latches until a power cycle); and
deploying 1.1.104 to the bench to confirm the A1 polarity change in a real run —
the core was built with it but has never run on hardware.
