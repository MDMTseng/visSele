## 第一部分:概念骨架

憲法只有兩條。這件事之所以能這麼小,是因為機構本身:

```
震動盤 ──→ 轉盤 ──→ 閘門 ──→ 相機 ──→ 噴料站(SEL1/SEL2) ──→ 排出機構
  ▲                                          │                    │
  │                                    噴中 = 被挑出              │
  └────────── 沒噴到的料件被收集,放回震動盤 ←──────────────────┘
```

**唯一的出料方式是「不被吹中」,而不動作 = 回流,不是報廢。** 所以任何**單次**
失誤 —— 掉幀、致動被抑制、判定遲到、對不上 —— 都退化成「多繞一圈」,而下一圈
是一次全新的、獨立的判定。代價是產能,不是品質。

因此:

> **能讓錯的料出去的,只有在每一圈都重複的錯誤。**

而「判定必須描述它所套用的那一顆」只有兩條失效路徑。憲法就是這兩條:

### C-1 配對:這份報告屬於哪一顆

**證據性,不是序數性。** 比對的是兩個實際發生的時刻:

```
物件的 cam_us   這一顆的相機觸發實際發生的那一刻(ISR 蓋章)
報告的 cam_ts   這一幀實際被拍的那一刻(換算到裝置時鐘)
```

沒有任何一步依賴計數或順序,所以**掉幀、多幀、亂序、重傳、主機端排隊都不可能
造成誤配**。有配到,那份報告就確實屬於那一顆 —— 即使觸發本身發生在「不該」的
位置也一樣,因為它問的不是「第幾張照片配第幾顆料」。

守護它的是唯一一條不等式:

```
2 × TOL_US ≤ min_detect_sep_us
```

它同時買到兩件事 —— **唯一性**(在場物件彼此至少隔 `2×TOL`,一個 frame 視窗內
最多一個候選)與**退休安全**(真物件已在 SWITCH 退休時,最近的存活鄰居也在
`2×TOL` 之外,超出 `TOL` 就被拒絕,所以是配不到而不是配錯)。

**但間距只是上界,不是需求。** 視窗真正該由什麼決定,見下面 C-1b —— 兩者差 18 倍,
所以「用間距去估視窗」會得到一個鬆到不會叫的警報線。

必須在設定寫入時強制,且往安全方向夾(視窗變窄只會停機)。出貨預設曾經是
sep 4000 對 window 5000,**方向是反的** —— 安全性當時是靠相機幀率意外撐住的。

**已知的唯一破口(I-11):** 時鐘誤差恰好等於物件間距的整數倍時位移完全抵銷,
offset 算出來是正確的,沒有殘差、沒有拒絕、沒有停機 —— 只有那一顆分錯。而且
**這是 lap-invariant 的**,回流救不了它。目前擋著它的是餵料的不規律
(sigma 是視窗的 12 倍),**不是程式**。

### C-1a 循環是安全的,而安全來自唯一性 —— bootstrap 與 top-up 不是同一件事

很容易誤以為「只有確定的配對可以教時鐘」。**實際上不是。** `gate()` 對每一份通過
視窗的普通報告都重新量測 offset:

```c
offset_us  = (int64_t)cam_ts - (int64_t)nearest_cam_us;   // measured, not blended
est_cam_us = nearest_cam_us;
```

所以維護路徑**本來就是循環的**:用 offset 去配對,再拿配對結果去取代 offset。
而它安全,靠的**不是**教它的人很確定,而是 C-1 的唯一性:

> a wrong offset puts frames outside the window, and outside the window it
> **stops instead of guessing**.

offset 一旦偏掉,幀就落到視窗外 → 拒絕 → 連兩次停機。它不會悄悄鎖到錯的值上,
因為是**取代**而不是混合(blending 才會慢慢被帶走)。

所以真正的區分是:

```
bootstrap   此時沒有 offset,什麼都配不了,只能靠「外面沒有別的東西」
            -> observe() 收 BOOT_N=8 個樣本取中位數,要求真多數
top-up      跟每一份普通報告完全同一件事,不需要任何特殊身分
            -> gate() 直接取代
```

**現行的 RECAL 把 top-up 當成 bootstrap 在做** —— 關閘門、等閒置、重收 8 個樣本。
它其實只需要一個能配對的幀。

推論:

- **生產期間不需要 recal。** 普通報告一直在維護 offset。需要補的只有**閒置期**,
  因為沒有報告就沒有維護。
- 而閒置期正好是關閘門不痛不癢的時候 —— 所以現行設計的成本沒有看起來大。
  **真正會痛的是閒置→忙碌的交界**:RECAL 剛開始、閘門關著,料流這時恢復,那些
  料就沒了,而且只記在 `rej_unstable`(它併了四個原因,見 T-3,所以看不出來)。
- **幻影式 top-up** 可以消掉那個交界損失:一顆走完整管線的虛擬物件,不關閘門、
  不需要閒置。它需要兩件事,而且都與配對論證無關:
  1. **絕不可致動**。今天 `ActRegister_pipeLineInfo` 連 SWITCH 一起註冊、
     `Run_ACTS` 不檢查 `sync`,所以幻影今天**會噴**。要在註冊時就不排 SWITCH,
     而不是在分派時多一個 if —— 少一個將來會被漏掉的地方。
  2. **T-7 必須先修**。把幻影變成常規機制,等於把那個罕見的雙生產者競爭變成
     連續的。

### C-1b 視窗是距離,不是時間 —— 由 0.3 mm 決定,不是由間距估

`delta = |cam_us − expectedCamUs(cam_ts)|` 不只是時鐘模型的誤差,它也含**觸發到
實際曝光之間的延遲變異** —— 而那一段料件是在動的。所以 delta 有一個直接的物理
意義:**這一顆在被拍下的瞬間,離我們以為的位置差了多遠。**

視覺定位與背光照明都吃這個位置誤差,所以需求是用 mm 給的:**位置誤差 < 0.3 mm**。

```
盤徑 240 mm → 周長 754.0 mm,60000 tick/轉 → 0.012566 mm/tick
邊緣速度 = 0.012566 × 2 × plate_freq  mm/s

plate_freq   邊緣速度      0.3mm 需要的視窗    現行 5000us 實際允許
10000        251.3 mm/s        1194 us            1.26 mm
15000        377.0 mm/s         796 us            1.88 mm
20000        502.7 mm/s         597 us            2.51 mm
26000        653.5 mm/s         459 us            3.27 mm
32000        804.2 mm/s         373 us            4.02 mm
```

**間距上界(sep 28571 → 14285 us)與位置需求(373–1194 us)差 18 倍。** 用間距
去估視窗,得到的是一個鬆到永遠不會叫的警報線:現行 5000 us 在生產速度下要等到
位置誤差累積到 **4 mm** 才會拒絕一幀。

實測 `delta_max` 51–54 us = **0.027–0.043 mm**,遠在需求內。**機器的行為是好的,
壞的是門檻。** 把門檻收到 0.3 mm 對應的值之後,它仍是實測值的 7–15 倍(還有餘裕),
也仍在 200 us 的雜訊地板之上(到 plate_freq ≈ 59700 才會衝突)。

**這是 §C 的鏡像錯誤。** §C 說「寬度是時間,位置是距離」,因為寬度被當成距離存,
所以在速度兩端都錯。配對視窗是反過來的同一件事:**它本質上是距離,卻被存成時間**
—— 存成固定 µs,位置容差就隨速度變動 3.2 倍(10000→32000),只在某一個速度上對。

正確的形式是把容差用 mm 指定,由韌體換算:

```
TOL_US = match_tolerance_mm / (0.012566 × 2 × plate_freq) × 1e6
```

三個邊界依序收斂,而且順序不能顛倒:

```
上界   TOL ≤ sep/2                      唯一性與退休安全(C-1)
需求   TOL ≤ 0.3mm / 邊緣速度            視覺定位與照明(這一條最緊)
下界   TOL > 量測雜訊(實測 ~50 us)      太窄就永遠配不到,機器停死
```

### C-2 取景:這一幀裡的是不是那一顆

配對答的是「誰的觸發拍出這一幀」,**不是「這一幀裡是誰」**。後者由 `CAM1_on`
的幾何校正決定,配對完全不保護它 —— `CAM1_on` 若差一個料距,配對仍然完美運作,
報告正確地回到物件 N,而幀裡是 N±1,而且**每一圈都一樣**。

守護它的是站點區域:一顆沒對準的料落不進 318×424 的框,或框裡同時出現兩顆,
兩種都變成 NA → 回流。所以幾何錯位**傾向於**退化成產能損失。但這是傾向,不是
保證 —— 若鄰居剛好正對框心,它會被判定,而那個判定會被套到錯的物件上。

**C-2 沒有像 C-1 那樣的不等式。** 它靠的是校正的正確性加上區域的窄度。這是目前
整份設計裡最弱的一環,而且它與 C-1 的破口是同一類:兩者都是 lap-invariant 的
系統性錯位。

---

**其餘的一切都不是憲法。** 致動失敗、計數器說謊、排空卡住、鏈路鎖死、設定被
忽略 —— 這些會讓機器停擺、讓產能流失、讓日誌騙人,但在這個拓撲下**不會讓錯的
料出去**。它們重要,但它們是第二部分。

## 第二部分:營運不變式

違反這些的代價是稼動率、產能、空氣、以及「日誌說的話能不能信」。**不是品質。**
分開列的理由是:憲法只有兩條,而把兩條和二十條混在一起,結果就是兩條也守不住。

每一條都標明它是哪一次量測或事故換來的。

### I-1 三個轉速量不可互換

```
PLATE_FREQ_SETPOINT   設定值。set_setup 寫、get_setup 讀。
PLATE_FREQ_TARGET     斜坡的目標。IDLE 時為 0,即使設定值不是。
PLATE_FREQ_CURRENT    實際轉速。
```

**確認寫入要讀 `get_setup`;要知道機器現在在做什麼要讀實際值。** 一個下午在三
個不同地方搞混三次(CAVEATS §A):RUN 按鈕拿 TARGET 去確認 SETPOINT 的寫入,
在 IDLE 永遠不可能通過;面板拿 TARGET 換算寬度,顯示差 6.7 倍。

**目前的實作違反這一條**:`get_running_stat` 與 `poll` 回報的 `plate_freq` 是
`PLATE_FREQ_TARGET`,而且沒有任何欄位回報實際轉速。要確認盤子真的停了,只能
對 `step_count` 微分。新實作必須提供實測轉速。

### I-2 → 已升格為憲法 C-1

不等式本身見第一部分。這裡只留下量測:2026-08-08,ROI 裁過、39/s,
`delta_max 54 us` 對 5000 us 視窗 = **92 倍餘裕**。§M 記錄的「速率相關殘差尾巴」
(全幅 30 Hz 時 3308 us)在裁 ROI 之後消失了。

### I-2b tid 是可以刪掉的,而刪掉它會消滅一整類危害

配對既然是證據性的(C-1),`tid` 就只是**被取代的那套序數機制**加上一個過渡期
的交叉稽核。遷移的終點本來就是 `PERIF_CORE_PAIRING 0`(核心不再配發 tid)。

刪掉它會一併消失的東西:

- `tid_counter` 的雙生產者競爭(T-7)最嚴重的後果 —— 重複 tid 讓判定落到錯的
  料件上。而 `byTid` 在存在時是**權威的**,它會蓋過時間戳的判斷,**從側面繞過
  C-1 的保護**。
- `tid` 在 2³¹ 的 `is<int>()` 失效、`CAL_TID_NEXT` 與真實 tid 的區間重疊、
  `INSP_RESULT_MATCHES_NO_OBJECT`(err 1)的整條路徑。
- 監控工具把校正物件的 tid 當成斷號的誤報。

**前提是先證明時間戳配對夠好**,而那正是 `agree/disagree` 存在的理由 —— 到目前
為止在真料上是 `agree` 數千、`DISAGREE 0`。刪除的順序:先讓 `disagree` 在足夠
長的真料運轉上維持 0,再拿掉 tid。

### I-3 寬度是時間,偏移是位置

站點偏移是位置(1 tick = 0.0126 mm),改速度不會移動任何東西的發生點 —— 這是
對的。**但寬度不是。** 相機的觸發下限、背光的上升時間、電磁閥的開啟時間,沒有
一個在乎距離。

同一個「50 ms @ 30 rpm」的吹氣寬度,在 3 rpm 是 500 ms、在 40 rpm 是 38 ms ——
一個儲存值產生 13 倍的散布,兩端都錯(CAVEATS §C)。

`ticks = ceil(us × 2 × PLATE_FREQ_SETPOINT / 1e6)`,**向上取整**,而且對
SETPOINT 而非 CURRENT 換算 —— 因為誤差不對稱:**太短漏掉一顆料,太長只花掉空氣
和 LED 工作週期**。SPINUP 期間因此會比要求的長,那是安全側。

### I-4 誤差方向的不對稱是設計原則,不是巧合

貫穿整份設計:

| 選擇 | 太多的代價 | 太少的代價 |
|---|---|---|
| 脈衝寬度 | 空氣、LED 工作週期 | 漏一顆料 → 回流 |
| 配對視窗 | **誤分選(唯一真正的品質風險)** | 停機 |
| 間距 | 產能 | **配對歧義 → 誤分選** |
| worst-wins | 良品被剔除 | 不良品不被吹 → 回流 |

**任何取捨都往「停機/浪費/回流」而不是「誤分選」的方向倒。** 新實作每遇到一個
夾制,都要能說出它倒向哪一邊、為什麼。

注意最後一列的更正:在這個拓撲下,NG 被 OK 蓋掉的結果是 `cat=3` → 不觸發 →
**回流**,下一圈重新判定,不是放行。真正不可回復的只有配對視窗那一列 —— 因為
誤分選會把料件**吹進錯的桶**,而被吹出去的料件不回流。

### I-5 嚴重度就是 cat 值,而且愈小愈嚴重

`SEL1` 是最嚴重的剔除,最後一個選別器是良品。`PERIF_CAT_NA = 0xFFFF` 比任何
選別器都大,所以「沒有判定」自動是最不嚴重的,真實判定不需要特例就能蓋過它。

**重複報告採 worst-wins**(`cat < 現值` 才覆蓋)。原本是無條件後寫者勝,那只有
一個壞方向:**NG 被後來的 OK 蓋掉,不良品就放行了**;反過來只是浪費空氣。

十個主機工具曾經全部把 `cat_ok`/`cat_ng` 設反(CAVEATS §P) —— 而幻影測試**永遠
抓不到**,因為沒有東西被吹掉,滑移檢查在任何重新標記下都自洽。真機上每一顆良品
都會進到剔除桶。

### I-6 相機的幀一定先於它的宣告抵達

校正邏輯依賴這一點(CAVEATS §E)。任何「先等宣告再處理幀」的實作都會死鎖。

### I-7 退出檢測模式不會停盤

`IDLE` 的迴圈本體是 `PLATE_FREQ_TARGET = PLATE_FREQ_SETPOINT`,所以 IDLE **每一
輪都在驅動盤子**。

- **STOP 必須寫 `plate_freq: 0`**,`exit_insp_mode` 單獨不會停。
- 因此停機會摧毀設定的轉速,想重啟的人沒有速度可用。WebUI 為此把最後的非零
  速度存在 localStorage,而且**寧可拒絕啟動也不代入編譯預設值** —— REF_FREQ 是
  30 rpm,一台正在 4.5 rpm 調機的機器不能因為有人按了停止就跳上去。
- **停著的機器上的速度滑桿不能寫入**,寫非零值會讓盤子開始轉。

### I-8 韌體不能 printf

`printf` 在這塊板子上寫到 UART0,而 UART0 **就是**主機鏈路。裸文字對裝置自己的
解析器是雜散位元組 → `INIT_CHAR_ERROR` → err 11 → **latched** → 機器停止,主機
看到死鏈路。

早上診斷並修好,十分鐘後在同一個檔案裡被一行新增的警告訊息重新引入
(CAVEATS §D)。用 `dbg_printf`(它會框成 `{"dbg":...}`)。

### I-9 周邊鏈路只有一個擁有者

核心獨佔序列埠;開發主控台是**後來者踢掉前者**。任何量測腳本連上去,前一個就
斷線 —— 三小時的 soak 會當場結束(CAVEATS §G)。

### I-10 治具必須證明自己的刺激

一個說不出自己注入了多少物件的 soak,沒有量到任何負載,而它的「clean」什麼都
不代表。

`regress_watch` 曾經送 `{"n":20,"sep_us":60000}` 而韌體讀的是 `count`/`period_us`
—— 而 `count=0` 是**取消**。所以每一個指令都是取消,幻影一顆都沒發,量到的是
真實閘門感測器的自然流量。板子在每一次回覆裡都寫著 `"count":0`,腳本把回覆丟掉,
證據在手上放了 4.5 小時(CAVEATS §I)。

**沉默不是通過。** 一個在第一小時就死掉的核心,每次輪詢都回 `(no answer)`,從未
被計數,然後印出「clean」。

### I-11 規律的餵料會讓一個靜默誤分選從 10% 變成 100%

`report_match_ts` 開啟時,**恰好一個位移值會誤分選**:物件間距的整數倍。因為
`offset_us = cam_ts - nearest_cam_us` 是實測而非混合,位移剛好抵銷,offset 算
出來是**正確的** —— 沒有殘差、沒有拒絕、沒有停機,只有那一顆料被分錯。

目前的保護來自**餵料的不規律**,不是來自程式:

```
真實到達間隔 n=24288:  p1 42982   p50 85107   p99 269893 us
                       mean 99796  sigma 60350 us
配對視窗                              5000 us
```

sigma 是視窗的 12 倍。一個等於中位間距的時鐘誤差,落進鄰居視窗的機率是 10%,
連兩次 1%,連五次 0.001% —— 每一次未命中都是拒絕,所以這種持續性誤差會在大約
三顆料內停機,最多分錯一顆。

**這個保證是餵料的性質,不是程式的性質。** 如果這台機器改用固定節距的載具
(分度盤、有料袋的盤),間距散布塌縮,命中率從 10% 走向 100%,而一個持續的
「一個間距」時鐘誤差會變成**永不停機的系統性誤分選**。任何讓餵料變規律的改動,
都必須重新推導這個數字(CAVEATS §L)。

### I-12 相機讀出時間決定速率上限,而 ROI 是槓桿

```
全幅 2448x2048   ResultingFrameRate 35.18 fps   曝光下限 28425 us
ROI  560x452                       184.89 fps               5409 us
```

出貨的 `min_detect_sep_us = 28571` 與全幅每幀 28425 us 差 0.5% —— 那個設定本來
就是照相機裁的。開閘門而不先裁 ROI,只會換到 `err 13 CAM_CLOCK_LOST`
(相機丟幀 → 回來的幀配到的最近物件掉出視窗 → 連兩次即停;**這是 fail-closed
正常運作**)。

實測(ROI 裁過、真料、300 秒 soak):**30.60/s 與 38.95/s 都乾淨**,
`inspected/admitted` 100%、UNANS 0。放寬間距到 `sep 2000 / window 1000` 可到
**49.16/s**,此時 `rej_rate` 歸零,剩下的限制是料件自己的節距。

### I-13 延遲預算在尾巴上,不在平均值

```
plate_freq 26000 → 步進 52000 tick/s
CAM1_on  9315 tick → gate→相機   179.1 ms
SWITCH  29900 tick → 相機→SWITCH  395.9 ms  = 答案預算
實測 39.85/s:  gate→報告 avg 207.2 / max 488.2 ms
                相機→報告 avg  28.1 / max 317.7 ms  = 預算的 78%
```

**平均只吃掉 7%,最差那顆吃掉 78%。** 運輸時間與盤速成反比,盤子一快預算就縮水,
那個 78% 立刻破表 → `err 2 OBJECT_HAS_NO_INSP_RESULT`。

## 第三部分:已知陷阱

看起來對、實際上不對的東西。每一條都是實作者會自然寫錯的方向。

### T-1 判定定案與實際致動之間隔著一整個站距

**這不是 fail-open —— 更正自 2026-08-08 稍早的評估。** 兩份稽核把它評為
「帶著可信 NG 判定的料件被放行」,我照轉了,而我們都不知道機構拓撲:**不被吹中
的料件回流**,所以被抑制的 SEL1 只是讓那一顆多繞一圈,下一圈重新判定。品質沒有
風險。留下的是三件事:計數器與現實不符、`VERD_LOG` 記著沒發生的剔除、以及產能
無聲流失。

SWITCH 分派時判定已經定案
(`CONSEC_UNANSWERED=0`、`autoRateOk()`、任務入列、`insp_status=DEL`),但真正的
`IO_ON` 在一個站距之後才執行,而且**到那時才重新檢查條件**:

```c
if(task->info) {
  if(SYS_FREQ_STABLE && !SYS_STEPPER_DISABLED && !DRY_RUN && SEL1_ACT_COUNTDOWN)
  { ... IO_ON(PIN_O_SEL1, IOI_SEL1); }
} else {
  IO_OFF(PIN_O_SEL1, IOI_SEL1);        // OFF 沒有任何條件
}
```

`SYS_FREQ_STABLE` 在任何速度變更期間都是 false,而閘門此時也停止收料 ——
但**已經在途中的 20–30 顆料照常抵達 SWITCH**。判定 SEL1 的那些不會被吹掉,
`SEL1_Count` 不增加,沒有錯誤碼,而 `VERD_LOG` 仍記著「已剔除」。

**規則:一旦判定被消費(計數器被重設、料件被標記完成),致動就必須發生,或者
必須有一個計數器記錄它沒發生。** 條件檢查要在判定當下,不是在致動當下。

而**持續**的致動抑制才是真正嚴重的那個(T-2b):所有不良品從此無限回流,產能
崩潰,而沒有任何地方會說原因。文件自己警告過 ——「回流是無限的,某顆料件如果
每次都被判 NA,它會永遠在系統裡繞圈,吃掉產能卻永遠不產出」。`cat=3` 被列為
陷阱也是同一個理由:加了 `SEL3_Count` 卻不觸發任何氣閥,「以為分選了、實際上
沒有」。

### T-2 已退休的物件狀態被改回去,排空就永久卡住

ISR 在 SWITCH 後無條件寫 `insp_status = DEL`,而排空只從尾端、遇到非 DEL 就停。
**任何讓已退休物件變回非 DEL 的路徑都會永久卡住排空**:

- 主迴圈在讀與寫 `insp_status` 之間被 ISR 插入(ISR 剛設 DEL,主迴圈蓋成 `cat`)
- `cat` 無驗證:主機送 `-1001` 就能通過 worst-wins 蓋掉 `DEL`(`DEL = -1000`)

結果:RBuf 漲到 100 → 每顆料 `GATE_REJ_BUSY` → 不觸發相機、不排 SWITCH 任務 →
`CONSEC_UNANSWERED` 也不再前進 → **機器在 READY、盤子轉著、送料開著,什麼都不
檢測也不報錯**。

**規則:退休要靠一個不能被覆寫的機制**(獨立的 flag、或從環中真正移除),而且
**主機送來的每一個值都要白名單驗證**。

### T-3 一個計數器只能有一個原因

`GATE_REJ_UNSTABLE` 同時計「步進停用 / 速度未穩 / 閘門關閉 / 乾跑」四件事,
名字和註解只說 unstable。

而停機會把 `PLATE_FREQ_TARGET` 設成 0,盤子從 32000 以 accel 2000 減速要 **16
秒**,期間感測器還在看到料,每一顆都記進 `rej_unstable` —— **所以它是停機的
後果,卻讀起來像原因**。我在 2026-08-08 就是這樣得出「三次 soak 失敗是盤速不
穩」的錯誤結論。

**規則:每個丟棄的原因一格。合併原因的計數器會把因果講反。**

### T-4 高水位會永遠 latch,而它們正好在開機接縫被設定

`isr_gap_max_us` 在三小時 soak 中從 t+136s 起就停在 12720 us —— 那是進入檢測
模式那道接縫留下的,運轉中的真實值被蓋在底下看不見。`loopmax_us`、
`svc/st/rx/tx_us`、`resid_max_us`、`delta_hist` 全部同樣。

**規則:每個 max 都要能被窗口化,而且窗口化不能順帶清掉別的東西**
(見 T-5)。

### T-5 診斷指令不能有副作用

`reset_running_stat` 裡有 `CAM_SYNC.reset()`。清掉時鐘之後 `recalService()` 在
`!CAM_SYNC.valid` 就直接 return —— **唯一能重建時鐘的服務被「時鐘要先有效」擋
住**。運轉中一旦重置,時間戳配對就永久退回 tid,而且沒有任何地方會說。

若核心端也不再配發 tid(`PERIF_CORE_PAIRING 0`,遷移的終點),三個候選全 NULL,
**每份報告都配不到 → err 1**,等於一顆遠端停機鈕。

`uinsp_test.py profile()` 在每個掃描點都做完整重置,所以整條吞吐量曲線都是在
時間戳配對關閉、`CAM_CLOCK_LOST` 保護失效的狀態下量的,而且回報 `agree=0 /
delta_max=0` 會被讀成「時鐘完美」。

**規則:診斷路徑不得改變控制狀態。要清統計就只清統計。**

### T-6 未知的設定鍵會被靜默忽略並回報成功

`set_setup` 不管認得幾個鍵都回 `ack: true`。設定重組之後,八個工具開場送
`plate_freq: 15000`、收場送 `plate_freq: 0`,**兩個都是 no-op** —— 每一次 soak
量的都是板子當下碰巧帶著的組態,卻回報成「照要求跑的」,而每一句「盤子已停」
都是在描述一個什麼都沒做的指令。

`regress_watch` 最尖銳:它的 `must()` 存在理由寫著「被拒絕的指令不算跑過」,而
`ack: true` 就這樣走過那道檢查。

**規則:認不得的鍵要拒絕,不是接受。** 這一條先做,上面那八個會在下一次執行就
大聲失敗,而不是安靜錯一週。

### T-7 治具與即時管線共用生產者

`newPulseEvent` 有兩個呼叫情境:ISR(`GateSensing`)與主迴圈(`phantomEmitOne`)。
共用且未保護的有 `tid_counter`、`_prePulse`/`_preTime`,而 `getHead()` **不保留
槽位** —— `getHead → 寫欄位 → pushHead` 不是原子的,兩個生產者可以拿到同一個
槽,各寫各的、各 push 一次,環前進 2 而只有一份資料,第二格是上一圈的殘留物件。

**重複的 tid 會讓判定落到錯的料件上**,而 `byTid` 在存在時是權威的 —— 它會蓋過
時間戳的判斷,從側面繞過 I-2 的保護。

目前靠「先 `set_gate_disable`」的慣例避開,不是靠結構。**把治具移出去,這個競爭
在結構上就不存在了。**

### T-8 幻影脈衝與真實料件不能同盤混跑

`phantomEmitOne` 曾經回填 `gate_pulse`(`now - L1A_on + 3000`),讓注入的物件
立刻抵達相機 —— 那造成 ACT 佇列的 FIFO 反轉,對真實料件的目標是 `now+9315`,
反轉之後全部過期。`act_late_max` 9079、`tq_hwm` 28/32、18 次溢位。

已於 2026-08-08 修掉(不再回填),`act_late_max` 9079→0,`tq_hwm` 28→2,
chaos 從未通過的種子變成 5/5。

**規則:注入路徑與感測路徑必須產生完全相同形狀的物件。**

### T-9 `clear()` 不是原子的,而順序會決定閥門的死活

`RESET_ALL_PIPELINE_QUEUE()` 是八次獨立清除,`ACT_SWITCH` **最後**才清 —— 一個
timer tick 落在 SEL2 清完與 SWITCH 清完之間,SWITCH 分支會把 SEL 任務推進剛被
清空的佇列,那些殘留致動會在排定的位置發射。

`IDLE` 進入時呼叫 `RESET_ALL_PIPELINE_QUEUE()` 但**沒有** `ALL_OUTPUTS_SAFE()`,
所以 `exit_insp_mode` 落在一次吹氣的 ON 與 OFF 之間,OFF 任務被丟掉,**電磁閥
卡在通電狀態**,而 IDLE 還在驅動盤子。

ERROR 路徑順序也錯:先 `ALL_OUTPUTS_SAFE()` 再清佇列,ISR 可以插在中間執行一個
ON 任務,然後它的 OFF 被清掉。

**規則:安全化與清空必須是一個不可分割的動作,而且安全化在最後。**

### T-10 NVS 存的是 wire JSON,改鍵名等於掉值

設定以 wire JSON 存,所以**重新命名一個鍵會讓舊 blob 靜默落回編譯預設值**。
`io_on_level` 出過這件事,而這台機器是 active-low —— 燈和吹氣在有料的盤子上
自己開了。

而且 `plate.freq` **永遠存不進非零值**:`cfgPersistDeny` 要求 `SETPOINT==0` 才
准存,所以存下來的組態永遠 `freq: 0`,機器的工作轉速根本不是它保存設定的一部分。

### T-11 flash 寫入會停掉指令快取,而 ISR 呼叫鏈住在 flash

只有 `onTimer()` 是 IRAM,`StepGo`/`GateSensing`/`Run_ACTS`/`newPulseEvent` 全部
是一般的 flash 常駐函式。每個 NVS 寫入路徑都走 `cfgPersistDeny()` 的
standstill guard —— **只有 `clear_saved_setup` 沒有**,它的註解在講 RAM 值不受
影響,但危險的是 flash cache。

這推翻了 RELIABILITY_ROADMAP 裡「ISR 呼叫鏈全面 IRAM 化 —— 決議不做」的前提
(「flash 寫入已收斂到單一入口且被 standstill guard 硬性攔截」)。入口有兩個。

### T-12 沒有範圍檢查的輸入

- `plate.freq`:完全沒有夾制。負值 → 斜坡收斂到負數 →
  `(uint64_t)(5000000.0f / -1000.0f)` 是 UB → 在 Xtensa 上飽和成 0 →
  `timerAlarmEnable(0)`。而且**存進 NVS,重開機還在**。
- `plate.accel`:`accel: 0` → `step = 3.4e38` → 盤子一個迴圈內從 0 跳到滿速。
- `sel_act` 的 `delay`:無上界。`delay(600000)` 把主迴圈鎖住十分鐘,
  `ISRTrigQ`(32 格)溢位,在飛的料件全部錯配。
- `set_sel1_cd` 少帶 `count` → 設成 0 → **SEL1 永久失效到重開機**,而本來要抓
  這件事的守衛是註解掉的死碼,`SEL_ACT_LIMIT_REACHES` 從沒被拋出過。
- `reboot_bootloader` 不需要確認,而 `crash_test`/`wdt_test` 都要 `confirm:true`。

### T-13 RESET 逃生門是位元組精確比對

`{"type": "RESET"}`(冒號後有空格,Python `json.dumps` 的預設輸出)**不匹配**。
鏈路一旦 latched,只有硬編碼那串位元組的工具救得回來,其餘只能斷電。

### T-14 `enter_insp_mode` 在零速下會進 READY 並打開送料

`plate_freq == 0` 時 CAL 正常完成(校正已經不需要轉動),SPINUP 的
`SYS_FREQ_STABLE && CURRENT == SETPOINT` 是 `0 == 0` 立刻通過,READY 進入時
`FEEDER_ON = true`。而 `PLATE_FREQ_CURRENT == 0` 時 timer alarm 是關的,
`GateSensing` 根本不跑 —— **送料一直把料堆到不轉的盤子上,狀態顯示 101 READY**。

**而每次停機後正好就是這個狀態**(I-7:STOP 必須寫 `plate_freq: 0`)。

能都對。證據偏向 tick 讀法(SWITCH 29900 ≈ 60000 的一半 = 閘門與吹氣站相隔
180°,物理上合理),那就表示對外的 metadata 錯了一半。

## 這份文件的用法

- **要修 1gen**:第三部分就是待辦清單,第四部分就是每一項的驗收。
- **要重寫**:第一部分是骨架,第二部分是必須重新實作的東西,第四部分是「這一版
  可以上線了嗎」的答案。
- **不管走哪條**:任何一條不變式被違反時,新增一列到第二部分,寫上是哪一次量測
  發現的。這份文件的價值在於**每一條都有代價**,而代價不寫下來就會被再付一次。
