# 第二代擴展探路筆記 — 6 相機 / 多打光 / 4 SEL

2026-08-22。**這是探路,不是計畫。** 沒有要現在做,寫下來是因為裡面的數字**現在量得到,
機器改了之後就回推不出來**。

情境:6 台相機,每台可能有 3 種打光(方向、波長…),4 個 SEL。

## 0. 結論先講

| 問題 | 判斷 |
|---|---|
| 配對機制本身 | **現行做法是對的,不要換** —— 窗 < 間距/2 ⇒ 配到就是正確。前提比直覺弱:只要「時戳 = 曝光瞬間 **+ 常數**」即可,常數會被 offset 吸收。真正未驗證的是**時戳屬於感測器域還是觸發域**,以及**改曝光/ROI 後沒有東西讓時鐘重學**(§3) |

| 配對放裝置還是核心 | **留在裝置合理** —— 但理由不是省頻寬,是 fail-safe 的位置 |

| 次要阻礙 | 三個單例資料結構;記憶體 +40 kB;**GPIO 數量 —— 這可能才是真正逼你換 MCU 的原因** |

## 1. 三個把「一台相機」寫進資料結構的地方

這是唯一需要動結構的部分,其餘都是量的問題。

### 1.1 `pipeLineInfo.cam_us` 是單一時間戳

```cpp
uint64_t cam_us;   // Device clock at the instant THIS object's camera trigger fired
```

一顆料件會被 6 台相機在 6 個不同盤面位置拍到 = 6 個不同的裝置時戳。而整個配對機制
(`byTs`、`expectedCamUs`、`gate()`)是拿**一個** `cam_us` 對**一份**報告。

需要 `cam_us[N]`,而且報告要帶 `cam_id`。**這是安全論證的地基**,驗證成本最高的一項。

### 1.2 `CamClockSync` 是單例

一個全域 `CAM_SYNC`,而且 `TOL_US` / `LOST_N` / `BOOT_N` 都是 class static。6 台相機
各有各的晶體、offset、漂移(今天實測 42–46 µs/s,峰值 105 —— 那是**這一台**的),
需要 6 份獨立紀律。

更麻煩的是 `syncPulseService`:校正脈衝的正確性建立在「發射時沒有其他物件在外」。
6 台相機要嘛序列化(成本 ×6),要嘛設計 per-camera 同步窗。

### 1.3 判定聚合不存在

`insp_status` 是單一 `int32`,設一次,worst-wins 假設單一寫入者。6 台各產一個判定後:

- 要幾台回答才算數?
- 4 台答了、2 台沒答,這顆算什麼?
- 「unanswered」現在是二元的,要變成「部分回答」

先前盤點已列為缺失(多相機判定聚合不存在),屆時會變成阻擋項。

## 2. 頻寬:聚合封包把它從不可能變成寬鬆

### 2.1 設計(ct 提的)

20 Hz 聚合封包,不做 per-event。數字陣列:

```
公告 device -> core   [封包表頭 | (obj_id, cam_id, ts_delta) x N ]
判定 core -> device   [封包表頭 | (obj_id, result) x N ]
```

### 2.2 實測基礎的算式

`230400 8N1 = 23040 bytes/s`。JSON `cam_trig` 每筆 **105 bytes**(韌體註解 `:8197`
的實測值),料件率 **23 件/s**(2026-08-22 實測)。

```
6 相機 x 3 打光 = 414 事件/秒

  JSON cam_trig 105 B/筆    43470 B/s = 188.7%   不可能
  packed 12 B/筆             4968 B/s =  21.6%   可行
  packed 10 B/筆             4140 B/s =  18.0%

判定方向  23 件/s x 6B = 138 B/s = 0.6%
20Hz 封包  每包約 21 筆事件 / 256 bytes
```

**189% → 22%,在現有的 230400 上。** 所以第二代**不一定需要換傳輸層,可以先換編碼**。

這也推翻了一個舊理由:文件記著「裝置端配對移除 `cam_trig` 公告流量,省 64%」——
省掉的是 **JSON 的胖**,不是事件本身。聚合+二進位之後,那個把配對推到裝置端的
理由幾乎蒸發。

### 2.3 不要用 MsgPack(熱路徑)

MsgPack 的價值是**自描述 schema**,而這裡每筆都是固定的 `(obj_id, cam_id, ts_delta)`。
定長 struct 陣列更小、更快、**而且沒有 parser 可以出錯**。ArduinoJson 雖然原生支援
MsgPack,但仍會建 DOM,對純數字陣列反而比手打包重。

MsgPack 留給欄位會變動的路徑(設定、遙測)。

**時戳用 delta**:封包表頭放絕對時戳,每筆放 `u32` 差值。50 ms 窗內 delta 遠小於
u32,一筆 12 B 可壓到 10 B,而且**避開 64 位元在 32 位元核心上的撕裂問題**。

### 2.4 兩個方向的批次不對稱

公告方向沒有截止線。判定方向有:

```
plate 10000   CAM->SWITCH 1029 ms   50ms 批次 = 4.9%
plate 26000   CAM->SWITCH  396 ms   50ms 批次 = 12.6%
```

現在 e2e 是 13–28 ms,所以 50 ms 批次比檢驗本身還大。目前速度沒問題,但
**要用打算跑的最快盤速去算,不是現在這台**。

折衷:判定封包在「批次滿」**或**「最舊一筆快到期」時提前送 —— 上限仍是 50 ms,
接近截止線時不等。

### 2.5 聚合改變失效模式

今天一個畸形封包讓韌體 latch 進 `SERIAL_PROTOCOL_ERROR`,整台聾掉。聚合後
**一個壞封包損失 21 筆事件而不是 1 筆**。所以:

- **每包要有序號** —— 掉包必須可偵測,否則安靜地少掉 21 個物件。同事件記錄設計
  第 0 節的原則:記錄系統必須能證明自己沒漏。
- **每包獨立 CRC + 能從下一個封包邊界重新同步**。不要延續現在「latch 之後只有
  RESET 能救」的行為 —— 這順手修掉 A7 那個 Tier A 缺陷。

### 2.6 附帶好處與附帶要求

順手解掉 `get_running_stat` 那 2.9 kB 佔用 TX **130 ms** 的問題 —— **前提是 TX 路徑
要有優先權**。現在 `perif_tx_lock` 是先到先服務,在 20 Hz 節奏下會變成週期性抖動源。

## 3. 現行配對機制為什麼是對的 —— 以及它唯一的未驗證前提

**這一節是整份筆記裡最該先讀的一段。** 它不是在比較選項,是在說明現在這個設計的
安全論證,免得日後有人「改進」掉它。(ct 提出,2026-08-22。)

### 論證:窗 < 間距/2 ⇒ 配到就是正確

> 只要相機可以保證 timestamp 就是曝光的那一個瞬間,只要 window 夠窄,
> 即使是隨機觸發,**有配對到的就是正確的 frame**。

關鍵在於:**配對不是在推論身分,而是在陳述一個物理事實。** 如果時戳就是曝光那一
瞬間,那麼「這張影格的時戳落在這顆料件的預期時間 ±window 內」等於「這張影像拍的
就是當時在那個位置的那顆料件」。

於是連誤配的概念都不太成立:隨機的雜訊影格若落在窗外 -> NOMATCH(拒絕,安全);
若落在窗內,它拍到的本來就是那一刻在那裡的東西。

韌體已經把這個論證編碼進去了(`LegacyFirmware.cpp:9361`):

```cpp
// window must stay under half
cap = SYS_MIN_PULSE_TIME_SEP_us / 2;
if (CamClockSync::TOL_US > cap) TOL_US = cap;
```

窗小於料件間距的一半 -> 任一時刻窗內最多一顆物件 -> 配到就是唯一解。

### 這也是為什麼「數觸發」是更差的方案

計數是**相對**機制,沒有絕對錨點。雜訊誤觸發時,機台計數 +1,而相機也真的收到那個
邊緣、也真的產生一張影格 —— **兩邊同步增加,分歧檢查看到一切正常**,而從那一刻起
每張影格都配到錯的料件,永久、無聲、沒有任何內部證據。

這正是韌體對 tid 的判詞:「有自信地做錯」。時戳是絕對的且自我驗證 —— 殘差本身就是
「這個配對合理」的證據,計數沒有等價物。

(EtherCAT 的 distributed clocks 同步的是**匯流排節點**,管不到相機內部的晶體,
所以它把機台側做到亞微秒,而跨相機那一步原封不動。對這個問題是 overkill。)

### 餘裕有三個數量級

要誤配到**鄰居**,時鐘模型必須錯到跨過「間距減窗寬」:

```
14286 - 5000 = 9286 µs 的模型誤差
以實測峰值漂移 105 µs/s 計 = 88 秒的無補償漂移
```

而 `recal_idle` 是 10 秒,加上 slope 連續補償把殘差壓在 7 µs。而且**漂移造成的失效
方向是安全的**:模型漂了,正確的影格落在窗外變成 NOMATCH(拒絕),不會落進鄰居的
窗。要落進鄰居得漂 9.3 ms —— 那不是漂移,那是時鐘死了。

順帶:窗是 5000 而不是 500,原因**不是**穩態需要(穩態只需 7 µs 的 700 倍),而是
覆蓋空轉後的暫態。韌體註解:*「收緊窗而不縮短 idle,只是把停機移到每次安靜之後的
第一顆料件」*。窗和 `recal_idle` 是綁在一起的兩個參數,不能單獨調。

### 前提比直覺弱:不是「等於曝光瞬間」,是「等於曝光瞬間 + 常數」

(ct 指出,2026-08-22 —— 這一段修正了本節原本寫得太強的前提。)

`observe()` 學到的是 `offset_us = cam_ts - cam_us`。若時戳鎖在曝光**結束**:

```
cam_ts - cam_us = (觸發->曝光開始的延遲) + 曝光時間 + (任何固定的標記偏移)
```

**全部是常數 -> 整個被 offset 吸收 -> 殘差完全不受影響。** 配對照常運作。

所以「時戳鎖在曝光前還是曝光後」其實**不重要**。真正該問的是別的問題。

### 真正該問的:感測器域,還是觸發域

| 時戳來源 | 意義 |
|---|---|
| **感測器域**(曝光開始/結束、讀出) | 是「光子何時被收集」的**證據** —— 自我驗證 |
| **觸發域**(觸發訊號抵達) | 只是**複述裝置已經知道的事** —— 脈衝到了,不代表有曝光 |

差別在**過觸發**:觸發落在前一張的讀出期間,相機延後或丟棄。若時戳鎖在觸發抵達,
它會說「準時」,而實際上**沒有曝光,或曝光在別的時刻** —— 也就是說,前面「電氣層」
那一節擔心的失效,在觸發域下是**不可見的**。

**實驗能區分到什麼程度**(修正前面寫的):掃曝光時間只能區分
{觸發抵達, 曝光開始} 和 {曝光結束, 讀出完成},**分不出前兩者**(兩者都與曝光長度
無關)。要釘死那一對,得靠相機的 `ExposureEnd` 事件,或刻意製造過觸發,看會不會
出現「有時戳但沒影格」。

實務上曝光開始與觸發抵達只差感測器的觸發延遲,對全域快門工業相機通常很小且固定。
**危險的不是那個差值,是相機能不能為一個它其實沒曝光的觸發吐出時戳。**

### 實際風險:改曝光會讓那個常數變動,而沒有東西讓時鐘重學

查碼確認,不是推論:

```
CAM_SYNC.reset()          只在 校正(:4552)/ reset_running_stat(:5968)
CAM_SYNC.resetEstimate()  只在 recal service(:4986)

SetExposureTime()         執行期可設(CameraLayer_HikRobot_Camera.cpp:1116)
exposure_time             在 def 的 cam_param 裡,換 def 就會換
```

**換 def、換曝光、換 ROI 都不會讓時鐘重學。** 而相機層自己知道這些互相影響
(`:1159`:「ROI、像素格式、長曝光都會移動 floor,所以要重讀」)。

後果分兩種,都不是誤配,但都會被誤診成硬體問題:

| ΔE vs 窗 | 行為 |
|---|---|
| **小於窗** | 殘差整體偏移;`gate()` 會從一般報告把 offset 慢慢拉回(自癒),但**期間的雜訊拒斥餘裕被吃掉**。曝光 50 -> 2000 µs 偏移 1950 µs = 5000 窗的 39% |
| **大於窗** | 每張都配不上 -> NOMATCH。舊韌體第一張就停機;現在累積到 `CONSEC_NOMATCH` 門檻才停。**方向安全,但看起來像配對壞了,其實是設定改了** |

**該補的**:任何相機重設定(曝光 / ROI / binning)之後**主動讓時鐘重學一次**,
而不是等它自己撞牆。一行呼叫的事,難的是知道要呼叫。

### 原本的未驗證前提,收斂後的版本

上面整段論證建立在「時戳 = 曝光瞬間」。**這一條你們自己的文件說沒驗證過**
(`UINSP_CAVEATS.md:1127`):

> 有界的曝光延遲(觸發落在讀出期間)仍未量,而且**不知道 `cam_ts` 指的是觸發抵達
> 還是曝光** —— 前者的話殘差對曝光時機一無所知。

相機層取的是 HikRobot 的 `nDevTimeStamp`
(`CameraLayer_HikRobot_Camera.cpp:359-364`,`MV_FRAME_OUT_INFO_EX` 的
`nDevTimeStampHigh/Low`,10 ns 單位),但那個值鎖在觸發沿、曝光開始、曝光結束、還是
讀出完成 —— 沒有人量過。

**差別不是學術的**:如果它是「讀出完成」,它會隨曝光時間和影像大小移動,殘差就不再
是配對正確性的證據,而是一個碰巧穩定的數字(因為曝光時間固定)。那時候「殘差 7 µs」
看起來一樣漂亮,但它證明的東西不同。

### 決定性的實驗(十分鐘,不需新硬體)

**方法 A —— 掃曝光時間**

```
曝光 50 µs   -> 量 (trig -> nDevTimeStamp) 的差值
曝光 5000 µs -> 再量一次

差值不變           -> 鎖在曝光開始(或觸發沿),前提成立
差值移了 ~4950 µs  -> 鎖在曝光結束或之後,殘差的意義要重新解讀
```

結論是二元的。現在 def 的 `cam_param.exposure_time` 是 50,相機層有設定曝光的路徑。

**方法 B —— 用相機自己的事件**

相機層已經有事件訂閱,但只訂了觸發線邊緣
(`CameraLayer_HikRobot_Camera.cpp:805`):

```cpp
static const char *kEvents[] = { "Line0RisingEdge", "Line0FallingEdge" };
```

多數 GigE Vision 相機還提供 **`ExposureEnd`**,事件自帶相機時戳。拿
`ExposureEnd - 曝光時間` 和影格的 `nDevTimeStamp` 一比,直接知道後者鎖在哪。
而那段程式碼的註解自己也寫了,這些事件目前「還沒有任何下游依賴」。

**順帶一個沒確認的設定**(同檔 `:817-822` 的註解):

> `TriggerSelector` 這段程式碼從來沒設定過,所以一直是韌體預設值 —— 而它決定了
> 「觸發模式開啟」到底是一個邊緣一張影格,還是別的意思

這正好會影響誤觸發/欠觸發的行為,值得一併確認。

### 電氣層的誤觸發 / 欠觸發,與驗證手段

判準(ct,2026-08-22):

> 電氣上的誤觸發、欠觸發最好是排除,**但如果沒有驗證手段,失效是致命的。**

「排除了」本身需要證據,而證據要**一直在**。以下逐一走過各種電氣失效,結論不一致。

**欠觸發(相機沒拍)** — 物件沒有報告 -> 停在 UNSET -> 被下一份報告掃成 SKIP ->
未判定、回流。**安全且可見**(`SKIP_Count`)。2026-08-21 那 74 顆就是這個形狀。

**誤觸發(雜訊在觸發線上產生邊緣)** — 相機真的曝光、真的產生影格,**而時戳是真的**:

- 落在所有窗之外 -> NOMATCH -> 拒絕。安全。
- 落在某顆物件的窗內 -> 配給它。而影像是在時刻 T 拍的,T 在物件 N 的窗內代表盤子
  當時就在 N 的位置 ±5000 µs 內 = **±1.07 mm**(214 mm/s)。所以**那張影像拍的
  確實是 N**,只是取景偏了。

**時戳不會對「光子是什麼時候收集的」說謊** —— 這是它比計數強韌的根本原因。

**但有一個真的會出錯的情況**:誤觸發的影格若落在窗內,物件 N 會收到**兩份報告**,
而 worst-wins(`cat < insp_status`)會讓差的那份覆蓋 —— 取景偏 1 mm 的那張很可能
量出 NG,把原本的 OK 蓋掉。**方向是安全的(誤殺不是誤放),但仍然是錯的,而且
今天完全偵測不到。**

### 三層驗證,失效方式各不相同

| 層 | 抓什麼 | 現況 |
|---|---|---|
| **統計** | 「這張不像真的」 | `delta_hist` 已在收,窗從沒依它調過 |
| **對帳** | 「總數對不上」 | `cam_trig.*` 計數器已存在,值是 `0/0/0`(未啟用) |
| **因果** | 「相機說它漏了」 | 事件機制已接好,只訂了線路邊緣 |

**統計層 —— 殘差分布本身就是偵測器,而窗現在寬了 700 倍。**

真實影格的殘差是 <=7 µs 的緊分布;雜訊影格若落在窗內,殘差是**窗內的均勻分布**。
統計上完全不同。而窗是 5000 µs —— 那不只是配對容差,**它同時是雜訊影格的接受孔徑**。

實測的 `delta_hist`(log2 分桶,從 32 µs 起):

```
[1916, 0, 1, 0, 0, 0, 0, 0]
 <32µs      128–256µs
```

1917 筆裡 1916 筆在 32 µs 以下,**有一筆落在 128–256 µs**。那一筆是真的偏移還是
雜訊,現在無從分辨 —— 但它正好說明:**窗該用這個直方圖去訂,不是用猜的。**

**兩段式窗**可以同時解掉「窗為暫態而設、卻被帶進穩態」的矛盾:

```
運轉中(模型新鮮、影格規律)    緊窗,例如 100–200 µs
空轉後 / recal 後的前 N 幀      寬窗,之後收緊
```

雜訊影格的接受機率降 25–50 倍,而且不觸犯韌體註解警告的那件事(「收緊窗而不縮短
idle,只是把停機移到每次安靜之後的第一顆料件」)。

**對帳層 —— 計數當偵測器是合理的,當配對機制才不是。**

這一點要和 §3 前面「數觸發是更差的方案」分清楚,兩者不矛盾:

- 計數當**配對機制**:脆弱。錯一次就永久錯下去,而且自洽、無證據。
- 計數當**對帳**:裝置知道發出幾個觸發,相機知道產生幾張影格,發散 = 電氣層有事。

它不能告訴你**哪一張**錯了,但能告訴你**有事發生** —— 而對「不驗證就致命」的失效,
「有事發生」正是需要的那一項。

`cam_trig.{ext_trig_count, frame_num, trig_minus_frame}` 已經存在,註解寫著「常數
偏移沒關係,**漂移的差值才是相機拒絕的觸發**」,但今天讀到是 `0/0/0`。**啟用它
幾乎沒有成本。**

**因果層 —— 相機自己說,比從差值推論強。**

`FrameStartOvertrigger` 這類事件是相機報告「觸發來了但我沒能拍」。相機層已有事件
訂閱機制(`CameraLayer_HikRobot_Camera.cpp:805`),但只訂了
`Line0RisingEdge` / `Line0FallingEdge`。

### 這三層全都站在同一個前提上

統計層的解釋依賴「殘差 = 配對誤差」,而那依賴 `cam_ts` 就是曝光瞬間。**若時戳其實
鎖在讀出完成,殘差分布那一層的解釋要整個重寫。**

所以上面那個十分鐘的曝光掃描實驗,不只是補一個未驗證的前提 —— 它是**整套驗證能力
的地基**。


### 對第二代的意涵

前提成立的話,**這個機制可以直接放大到 6 台相機**:每台一份時鐘紀律、每台一個窗,
而「窗 < 該台的料件間距/2」這個條件對每台獨立成立。不需要換配對機制,也不需要
PTP —— PTP 只是讓殘差從 7 µs 變成接近 0,省掉 slope 補償,是優化不是必要。

前提不成立的話,**要先修的是這裡,不是別的地方**。

## 4. 配對留在裝置還是搬回核心

### 3.1 核心端的實作已經不存在了

先更正一個過期記載:`DEV_COMPLETE_CHECKLIST.md:290` 說「`PerifTriggerPairing.hpp`
645 行、`PERIF_CORE_PAIRING` 21 個條件點還在」。**查過了,不在了**:

```
PerifTriggerPairing.hpp              找不到
PERIF_CORE_PAIRING 在 wiringPanel.cpp  0 次
只剩五份 .md 還在講它
```

主機端那份已經拆乾淨。搬回去是**全新實作,不是復活**。
(五份 .md 都該標記過期:`DEV_COMPLETE_CHECKLIST` / `FIRMWARE_CONTRACT` /
`MACHINE_FLOW` / `PAIRING_MIGRATION_STATUS` / `InspectionCore/docs/UINSP_VERDICT_PATH`。)

### 3.2 不能一起搬回去的東西:tid 配對

```
舊機制是「tid 在場時 tid 說了算,時戳只是旁觀」…現在它有害:
當時戳無法定位一個影格時退回用 tid,正是時戳當初要取代的那種「有自信地做錯」。
時鐘放不了位置的影格,這台機器不可以拿去分選。
```

當初的判斷是**機制**(tid vs 時戳),不是**位置**(裝置 vs 核心)。核心完全可以自己
做時戳配對。若要搬,安全的形狀是:

```
裝置 -> 核心   {tid, cam_us} 公告          裝置端的物件時間軸
核心           用自己的影格時戳做時戳配對    安全關鍵的一步,在有影像的地方做
核心 -> 裝置   {tid, verdict}              tid 只當識別碼,不當配對依據
裝置           查不到就拒絕(fail-safe)
```

### 3.3 但算力不是理由 —— 配對很便宜

實際按迴圈算過(線性掃描 RBuf,每次迭代約 20 cycles):

```
配對
  今天              23 報告/s x  42 深度 = 0.008% of 240MHz
  6cam x 3light    414 報告/s x 200 深度 = 0.690%

expectedCamUs 的 64-bit 乘除(32 位元核心無硬體除法,抓 500 cyc)
  今天    0.005%
  6x3     0.086%
```

**加起來不到 1%。** 估錯 5 倍也才 4%。所以:

- **「配對 CPU 忙不過來」在數字上不成立**,第二顆 CPU 瞄準的是不存在的問題。
- 「不全盤面掃描」的優化**現成可用但不需要**:RBuf 依閘門順序排列,時戳搜尋可以
  二分或有界窗口。留當備案。
- 封包帶 `cam_id`,所以搜尋只在該相機的時戳裡進行 —— 還是 N,不是 6N。這個格式
  剛好避開了放大。

### 3.4 所以:留在裝置

理由**不是**省頻寬(聚合已經消掉那個理由),而是:

- 算力真的夠
- **裝置端配對是 fail-safe 的天然位置** —— 主機掛掉、連線斷掉時,裝置仍能自己判斷
  「這個影格我放不了位置,不要分選」。搬到核心之後這個底線得另外再造。

## 5. 真正的阻礙:ISR

`Run_ACTS` 在 IRAM,每個 tick 對**每個佇列**檢查一次。現在 8 個佇列
(SWITCH / CAM1 / CAM2 / L1A / L2A / SEL1-3),6 相機 3 打光 4 SEL 會變成 **23 個**,
per-tick 工作量約 3 倍。

**而現況已經不乾淨:**

```
isr_dur_max_us    40 µs
isr_overrun_n     279 次        <- 沒有人解釋過
isr_gap_max_us    303–369 ms    <- 沒有人解釋過
```

在一個已經有 279 次超時的 ISR 上乘 3 倍,是整份筆記裡我最擔心的一項。

而且 `ISR_SEG_MAX_CY[]` **只有 4 個分段**,23 個站台的細部時間量不出來 —— 會看到
總時間變長但不知道花在哪。

**第二顆核心若要用,應該用在 ISR / 致動排程,不是配對。** 但 ESP32 兩顆核心共用
記憶體匯流排和快取,而 `Run_ACTS` 依賴 IRAM 和關中斷的臨界區 —— 這比較像「換 MCU」
層級的決定,不是「開第二顆核心」。

## 5.5 站台表示法:每個相機站應該是「一個帶狀態的 task」,不是 N 個獨立邊緣

**這一節修正 §5 的結論**,不是補充它:站台數的線性成長是**現在這個表示法**的性質,
換掉表示法就不成立。(ct 提出,2026-08-22。)

### 現在:每個邊緣是一個獨立事實

```cpp
struct ACT_INFO {            // :1775
  pipeLineInfo *src;
  int info;                  // 電平 0/1
  uint32_t gate_pulse;       // 錨點
  uint32_t offset;           // 位置
};
```

一個站台 = 一串**彼此無關**的 `(位置, 電平)`。多打光的序列現在只能這樣表達:

```
L1A_on  = 654    L1A_off = 672
CAM1_on = 654    CAM1_off = 672
L2A_on  = 654    L2A_off = 672     <- 這些「相等」是巧合,不是約束
```

**問題不是跑不動,是表達不了序列的意義:**

- **「L1 熄的同一瞬間 L2 亮」是兩個碰巧相等的數字。** 沒有任何東西保證。有人只改
  一個 -> 兩盞燈同時亮(曝光錯)或全暗(黑圖),而且**不會有任何錯誤**。
- **「燈要先穩定才能開快門」是數值的性質,不是結構的性質。** 設定驗證表達不了
  `L1_off >= CAM1_on + 曝光`,因為它看到的只是三個獨立整數。
- **設定爆炸**:46 個獨立可設欄位,真正的自由度只有「站台位置 + 每步(燈, 穩定,
  曝光)」,其餘都是可推導的。

### 應該是:一個站台 = 一個帶狀態的 task

```
L1 on -> shot -> (L1 off, L2 on) -> shot -> (L2 off, L3 on) -> shot -> L3 off
```

三個問題全部變成**結構上不可能發生**:狀態機只有「當前這一盞燈」,所以兩盞同時亮
寫不出來;順序是狀態轉移不是大小關係;設定變成 `(位置, [(燈,穩定,曝光) x N])`。

### 這直接解掉 §5 的 ISR 擔憂

```
現在的表示法:  6 相機 x 3 燈 x 2 邊緣 + 6 快門 x 2 = 48 task/物件,23+ 佇列
狀態機表示法:  6 個站台 task/物件,6 個佇列
```

`Run_ACTS` 每 tick 從「檢查 23 個佇列」變成「檢查 6 個」—— **比現在的 8 個還少**。
所以第二代在 ISR 上不是變重,是變輕。§5 那段「乘 3 倍」的擔憂只適用於沿用現在的
表示法;**但 §5 裡「先查清楚 279 次 overrun」的建議不變**,因為那是現況的未解問題,
與第二代無關。

### 三個實作上要小心的地方

**1. 快照紀律要保留,但變得更容易。** 現在的設計有個好性質(`:1268` 附近的註解):

> A task carries its anchor and the offset it was pushed with, so an object's ON
> edges are the ones that were current when it was admitted.

狀態機若**邊跑邊讀設定**,會在序列中途看到設定變更 —— 正是 `SPO_active`/`SPO_snap`
指標交換要防的問題往下移一層。修法是**入列時把整個序列參數快照進 task**。這比現在
容易,因為快照粒度變粗(一個站台一次,而非 8 個邊緣各一次)。

**2. 重疊直接報錯,不要夾限。**(ct 的決定,2026-08-22。)

現在 `ACT_TRY_RUN_TASK` 在 task 落後時,會把 offset **夾到「下一個物件的位置」**
以免越過它(`ACT_CAP_N` / `ACT_CAP_MAX_T`):

```cpp
_cap_ = (uint32_t)(_nx_->gate_pulse - task->gate_pulse) + _nx_->offset;
if(task_off > _cap_) { ... ACT_CAP_N++; task_off = _cap_; }
```

**夾限是安靜的降級。** 被夾住的意思是致動發生在**和設定不同的位置** —— 相機站台
就是影像在錯的位置拍的,SEL 就是空氣在錯的位置噴的,而且外面看起來一切正常。
`ACT_CAP_N` 有在數,但沒有人在看。

狀態機版本裡我原本留了一個開放問題(「中止序列還是壓縮曝光?」)。**兩個都是錯的
答案**:兩者都會產生看起來正常的錯資料。重疊代表的是「這組序列在這個速率下放不
進料件間距」,那是**設定與速率的矛盾**,不是執行期要吸收的狀況。

這和這台機器自己一貫的哲學一致:*「停機是可以看見的,悄悄分錯的料件不是。」*

而且重疊**可以在三個時間點偵測,越早越好**:

| 時機 | 檢查 | 動作 |
|---|---|---|
| 設定時 | 序列總長 vs `min_detect_sep_us` | 拒絕這組設定,並說出差多少 |
| 入列時 | 這顆的序列會不會壓到前一顆的 | 拒絕入閘 —— `GATE_REJ_BUSY` 已經存在,語意也吻合 |
| 執行期 | 仍然發生 | **報錯停機**,因為代表前兩層的假設破了 |

前兩層讓「速率太快」變成一個**操作員在調機時就會看到**的訊息,而不是生產中才浮現
的良率問題。第三層是最後防線,而它應該是不可能到達的 —— 到達就表示有 bug。

**現在改的風險比看起來低**:`ACT_CAP_N` 至今是 **0**,那條路從沒被走過
(Tier A 的 "correct-by-construction and remains unexercised")。所以沒有既有行為
依賴夾限 —— 但也代表**沒有既有行為可以拿來對照驗證**,新的錯誤路徑要自己造測試。

注意要和 `ACT_GROW_N` 分開:grow(2324809 次)是 live offset 比入列時的 offset 大,
那是正常的;cap(0 次)才是越過下一個物件。**只有後者是重疊。**

**3. 中止路徑是新的失效模式。** 現在一個過期的邊緣就是「該放就放、清空就沒了」。
狀態機可能**卡在中間狀態** —— 機器停了、物件退場了,而 L2 還亮著。需要一個明確的
abort 轉移把所有燈關掉,而且必須在 `RESET_ALL_PIPELINE_QUEUE`(`:1933-1940` 那串
`.clear()`)那條路上被呼叫到。**現在沒有這個問題,狀態機會製造它。**

## 6. 次要阻礙

### 5.1 記憶體:物件要活得更久

6 台相機分散在盤面,物件必須活到**最後一台拍完**才能退場,所以 RBuf 要加深。

```
              時戳數   每物件    深度100    深度200
今天            1      68 B      6.6 kB    13.3 kB
6cam x 3light  18     204 B     19.9 kB    39.8 kB
```

40 kB 在 320 kB 的 ESP32 上付得起(現在用 17.8%,free heap 183 kB),但不是免費的,
而且是連續的靜態配置(`RingBuf_Static<pipeLineInfo, PIPE_INFO_LEN>`,`:1730`)。

### 5.2 站台表是手工維護的具名欄位

`stagePulseOffset`(`:1233`)現在 15 個具名欄位。6 相機 3 打光 4 SEL = **23 站 ×
on/off = 46 個欄位**,而同一組名字重複出現在 **7 個維護點**:

struct 定義 / 預設值 / `get_setup` / `set_setup` / NVS schema /
WebUI `STATIONS` 表 / `uinspCfg.js` 的 `CFG_GROUP`

整合計畫裡「給設定一個 struct 的家」從「可做」變成**前置條件**。

### 5.3 GPIO 數量

23 個站至少 23 支輸出腳,加 gate、stepper、IO —— ESP32 可用的大約就那麼多。用擴充
晶片會引入延遲,而這些邊緣是微秒級精度的。**這可能才是真正逼你換 MCU 的原因**,
不是 CPU 也不是記憶體。
