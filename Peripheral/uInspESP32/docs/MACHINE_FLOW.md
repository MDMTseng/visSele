# 全檢機:流程、憲法、與每一段的量測目標

這份文件存在的理由很具體:**同一組時間戳的參考點,在 2026-08-08~09 這一天被
重新推導了至少三次**,其中一次還被當成回歸故障追了一小時。每次 session 壓縮
之後,「`report_latency` 是從哪裡量到哪裡」這種事就得從程式碼重新讀一遍。

所以這裡記的不是結論,是**參考點與量測目標**:每一段是什麼、用哪個時鐘、
哪個計數器在看它、那個計數器**看不到什麼**、以及什麼情況下那次量測是廢的。

數字一律標記 **[驗]**(有量測支撐)或 **[推]**(從程式碼推導,未量測)。
不要引用沒有標記的數字。

---

## 一、物理流程

```
震動盤 ──> 轉盤 ──> 閘門感測器 ──> 相機 ──> 噴料站(SEL1/2/3) ──> 排出 ──> 回流
                     ^gate_pulse    ^CAM1_on        ^SWITCH / SEL*_on
                     tick 0         +654            +29900 / +30000..31520
```

**回流不是報廢。** 噴口不動作 = 料件回到震動盤重跑一圈。只有「在某一圈裡
把判定發給錯的物件」才會出貨壞品 —— 這是整套設計的安全邊界,也是為什麼
「停機而不猜」永遠優於「猜一個」。

**tick 率 = `2 x plate_freq`** —— **[驗]**,V-31 已解(2026-08-09)。

驗法:量「閘門->相機」的行程時間,對照 NVS 裡的 `CAM1_on`。

```
plate  5000  travel 915.6ms   9315/(2f) 預測 931.5ms   1.7%
plate 10000  travel 462.2ms             預測 465.8ms   0.8%
plate 20000  travel 231.5ms             預測 232.9ms   0.6%
```

**重要**:`CAM1_on` 的**實際值是 9315(NVS)**,不是原始碼裡的預設 654。
拿編譯預設去推導會差 14 倍 —— 這個錯今天犯過一次。
**要看偏移一律 `get_setup`,不要讀原始碼。**

由此,預算可以標 **[驗]**:

```
CAM->SWITCH = (29900 - 9315) / (2 x plate_freq)
  plate 10000 -> 1029 ms
  plate 26000 ->  396 ms
```

## 二、憲法(只有兩條)

**C-1 配對是證據性的,不是序數性的。**
判定屬於哪一顆,由「報告攜帶的相機時間戳」與「該物件的相機觸發時刻」比對決定,
不靠計數、不靠順序。護欄是 `2 x TOL_US <= min_detect_sep_us`
—— 視窗內只能有一個候選,唯一性由間距保證。

**C-1a** 維護是循環的:`gate()` 從**每一份通過視窗的報告**重新量測 `offset_us`
(最後一行是整個覆寫,不是混合)。安全性來自唯一性,不是來自教師的正確性。

**C-1b** 連續 `LOST_N` 份報告的最近物件落在視窗外 → `CAM_CLOCK_LOST` 停機。
**停機是設計行為**,不是故障。

**C-2 取景是幾何性的。** 相機在 `CAM1_on` 觸發,由 tick 計數決定,與報告無關。

其餘一切(節流、skip 政策、auto_rate、重新校準時機)都是**運作層**,
可以改、可以關,不影響上面兩條。

## 三、時鐘與參考點(**最常被搞混的部分**)

| 名稱 | 誰蓋的 | 蓋在什麼時刻 | 用途 |
|---|---|---|---|
| `trig_us` | 板子 `newPulseEvent` | **閘門偵測到料件** | `report_latency` 的起點 |
| `cam_us` | 板子 CAM ISR | **相機觸發脈衝發出** | 配對的基準(64 位元) |
| `cam_ts` | 相機硬體 | 相機自己的時鐘 | 報告攜帶,與 `cam_us` 比對 |
| `host_rx_us` | 核心 | 影像推進 `inspQueue` | 核心端拆解 |
| `host_insp_us` | 核心 | 進入 `ImgPipeProcessCenter_imp` | 核心端拆解 |
| `enq_us` | 核心 | 報告推進 `perifSendQueue` | 核心端拆解 |

**`report_latency.avg_us` = `trig_us` -> 報告被處理 = 閘門 -> 判定**,
含料件走路。韌體的欄位註解自己寫著 `for the gate->report latency stat`。
**拿它對 CAM->SWITCH 預算是比錯區段**,這個錯誤在同一天犯了兩次。

**要用的是 `report_latency.cam_avg_us` / `cam_max_us`**(2026-08-09 新增),
從 `cam_us` 起算 = **相機觸發 -> 判定 = 電子延遲**,與預算同一個起點。

**[驗]** 三個盤速下的拆解:

```
plate  5000   gate->rep 929.6ms | cam->rep 14.1ms | travel 915.6ms
plate 10000   gate->rep 475.9ms | cam->rep 13.7ms | travel 462.2ms
plate 20000   gate->rep 245.7ms | cam->rep 14.2ms | travel 231.5ms
```

**電子延遲不隨盤速變化(14ms),行程時間完美反比。**
`cam_max_us` 是 253-259ms —— 對 plate 26000 的 396ms 預算,
**最壞的一份報告用掉 65%**。限制吞吐的是尾巴,不是平均。

## 四、每一段的量測目標,以及它看不到什麼

### 閘門
- `gate.accept` / `edges`:收下的 / 感測器邊緣總數。
- 拒絕分四格:`rej_rate`(節流)、`rej_width`(脈寬)、`rej_unstable`(轉速不穩)、
  `rej_dist`(距離)。**合成一格會互相掩蓋** —— 這是拆開的原因。
- **看不到**:被相機拒絕的觸發。相機在過觸發時是**丟棄**而非排隊
  (**[驗]** 200 發 400Hz → 94 幀,frame_id 連續無跳號),所以那些觸發不留痕跡。
  相機自己數得到:`FrameSpecInfo` 的 `ExtTriggerCount`(偏移 4,32-bit LE)。

### 相機 / 取像
- `cam_sync.sync_pulses` / `learned` / `cal_runs` / `cal_fails`。
- **看不到**:`AcquisitionStart` 失敗。核心會 `LOGE` 一筆然後**照常運行**,
  板子端看到的是「打脈衝、零報告、最後 `CAM_CLOCK_CAL_FAILED`」,
  與時鐘故障**無法區分**。這一天有兩次一小時等級的誤診來自這個沉默。

### 檢驗
- 核心端 `insp split`:`queue`(等待被檢驗)/ `inspect`(運算本身)。
- **[驗]** 有配方(10155,工位 318x424)時 `inspect avg 9.78ms / max 96.19ms`。
- **[驗]** 沒有配方時 `inspect avg 2.02ms` —— 那是「不檢驗」的成本。
  **沒載配方的延遲量測缺了最大的一塊,不要當產線數字用。**
  判準:`count` 全是 `NA` 就是沒載配方。

### 報告送出
- `perif write`:`write`(串列寫入)與 `wait`(佇列等待)**分開**。
  合成一個數字時兩者會互相掩蓋 —— 平均由前段主導,尾巴由後段主導。
- **[驗]** `write avg 0.47ms / max 158ms`;`wait avg 2.98ms / max 808ms`,`qdepth 0`。
  `qdepth` 是 0 卻等 808ms → **是送出執行緒被餓死,不是積壓。**

### 配對
- `agree` / `disagree` + `CAMSYNC MISMATCH tid=.. ts_tid=.. d=..` 明細。
  **偏移量比次數有用** —— 常數偏移與雜訊是完全不同的病。
- `delta_hist`(log2 分桶)比 `delta_max` 有用:視窗要蓋住**合法發生的最壞殘差**,
  而 max 分不出「一顆離群」與「經常接近」。
- **[驗]** 有配方時,三個盤速全部 `disagree 0`,一個 MISMATCH 都沒有:

```
plate  5000   agree=723   disagree=0   offsets {}
plate 10000   agree=1106  disagree=0   offsets {}
plate 15000   agree=1368  disagree=0   offsets {}
```

- **已撤回**:無配方時同樣的掃描給出 100% 分歧、偏移 +1/+2/+4 隨盤速成長,
  並曾寫成「序數配對落後在途報告數 = 速率 x 延遲」。那條**完全是無配方狀態的
  產物**,有配方時分歧是零。不要引用它。

  無配方為何會這樣,**未解釋** —— 而且不需要解釋才能撤回。
  重點是:**在全 NA 的狀態下量到的任何配對行為都不算數。**

### 噴料
- `count`:`SEL1/2/3` / `NA` / `UNANSWERED` / `SKIP`。
- `UNANSWERED` = 物件到 SWITCH 時還沒有判定(`err 2 OBJECT_HAS_NO_INSP_RESULT`)。
- **看不到**:`report_latency` **只在報告到達時累加**,所以太晚到或沒到的
  那些**不在統計裡**。avg/max 是倖存者的分佈,而害死機器的正是缺席的那條尾巴。

## 五、什麼情況下這次量測是廢的(逐項檢查)

這一天有五次「量到空的」,每一次看起來都像可靠證據:失敗可重現、症狀一致。

1. **沒載配方** → 判定全 `NA`,檢驗成本缺席。查 `count`。
2. **沒送 `stepper_enable` 或盤速 0** → `sync_pulses=0`,校準必敗。查 `pulses`。
3. **沒設 `INSP_PERIF_VERDICT_PATTERN`** → 判定全是 NA(65535),
   「零錯置」這個通過條件**不可能失敗**。`jitter_sweep` / `regress_watch` 需要它;
   `soak_real` **絕不能**有它(它要真實判定)。
4. **孤兒 core** → 舊的 core 仍持有相機與序列埠,新的拿不到影像。
   開跑前數一次 `pgrep -f mac-arm64/visSele`。
5. **相機不出圖** → `AcquisitionStart` 回 `USB3Vision write_memory error`,
   而列舉與設定都正常。`DeviceReset` 每次都救得回來(**[驗]** 五次),
   但**要在沒有 core 持有裝置時才問得到**。
6. **視窗被夾** → `match_window_us` 會被夾到 `min_detect_sep_us/2`,
   而工具印的是它**請求**的值。掃視窗時 `min_detect_sep_us` 必須同步放大。
7. **一顆種子跑一整排** → 掃描的各列不獨立時,量到的是同一個事件的多份複本,
   而且**在最沒有資訊量時看起來最紮實**(各列高度一致)。

## 六、開著的問題

- **端到端的組成:已確認是行程,不是電子延遲。** **[驗]**
  盤速 5000 / 10000 / 20000 -> 924 / 479 / 276 ms,**隨盤速反比變化**。
  固定的電子延遲不會這樣縮。核心端只佔約 13ms(inspect+queue+wait+write),
  其餘是料件從閘門走到相機。
  (量測注意:兩段之間沒有 `reset_running_stat`,第二段是累計值,
  276ms 是減回去算的 —— 掃描前先重置。)

  **但 tick 換算對不上**:`CAM1_on=654`,若 tick 率是 `2 x plate_freq`,
  盤速 10000 應該只有 33ms,而實測是 479ms(約 4700 tick-等效)。
  這正是 **V-31** 那個 2 倍量綱歧義的實際後果 —— 在它解決之前,
  **任何用 tick 換算出來的時間都不要當 [驗] 用**,包括 CAM->SWITCH 的預算。
- **送出執行緒的喚醒延遲**(原記為「餓死」)。**[驗]** 已定位到一側:

```
WAIT SPIKE  82.9ms: idle_before 206.6ms, depth_at_pop 0 -> 執行緒 IDLE
WAIT SPIKE 148.0ms: idle_before 282.7ms, depth_at_pop 1 -> 執行緒 IDLE
```

  `idle_before > wait`,表示東西進佇列時執行緒**已經在閒置**。所以不是積壓。
  `TSQueue` 用的是正規 `condition_variable` + `notify`,所以也不是漏通知。
  而 `wait` 的定義就是 push -> pop,在佇列空、執行緒閒置時它**就等於
  notify -> 執行緒真正被排到**的時間。

  **剩下的候選只有兩個:OS 排程延遲,或 `mutex_` 被長時間持有。**
  下一刀:在 `push` 內 notify 前後各蓋一個時間戳,把「通知本身」與
  「被排到」分開。

  影響目前有界:`cam_max_us` 187-259ms,對 plate 20000 的 514ms 預算
  仍有餘裕,但對 26000 的 396ms 只剩 35%。**這是提吞吐的門檻。**
- **配對偏移結論存疑**(見上)。
- **WebUI 無法設定機器**:`SETTABLE_KEYS`(`src/script.jsx:1555`)全是平鍵,
  裝置只收群組,而裝置對未知鍵**靜默忽略但回 ack true**。
  畫面症狀:按下啟動後出現「轉速沒有寫進裝置,未進入檢測模式」。
- **曝光參考點**:`cam_ts` 指的是觸發到達還是曝光開始?前者的話,殘差對
  「照到哪一顆」一無所知,得靠外部光感測器才問得到。
- ~~**V-31**:`pulses_per_rev` 的 2 倍量綱歧義。~~ **已解**(見第一節)。

## 附錄:報告路徑的延遲 —— 完整拆解、排除紀錄、重現方法(2026-08-09)

### 結論(全部 [驗])

```
gate -> report           480 ms @plate10000   料件走路;隨盤速反比
  └ camera -> report      14 ms (avg)         電子,不隨盤速變化
      ├ inspect          9.78 ms avg / 96 max  有配方;無配方時 2.02ms
      ├ queue(等檢驗)   0.13 ms avg / 55 max
      ├ wait(等送出)    0.59 ms avg / 112 max
      └ write(串列)     0.39 ms avg / 215 max  ← 尾巴第一名
            ├ 等鎖       0.0 ms avg / 0.1 max   perif_tx_lock 沒被搶
            └ 上線       215 ms                 write() 被阻塞

預算 CAM->SWITCH = (29900 - 9315) / (2 x plate_freq)
  plate 10000 -> 1029 ms      plate 26000 -> 396 ms
```

**平均完全不是問題(14ms 對 396ms),尾巴才是。**
單次 215ms 的串列阻塞會把料件推過截止線:出現該狀況的那一輪
`UNANSWERED` 是 31,平時是 4-10。

### 為什麼 215ms 不是頻寬

230400 baud 下 215ms 可以送 6KB,而一個報告封包約 100 位元組。
整條線的實際流量約 11 筆/秒 x 100B = **1.1KB/s,對 23KB/s 的容量**。
所以是 `write()` 呼叫被阻塞(驅動或裝置端 TX 緩衝),不是在傳資料。

**追下去的結果(2026-08-09):**

- **流控排除**:核心用 `"8N1"` 開埠,`simple_uart` 只在 `F` 選項下開
  `CRTSCTS`,所以硬體流控是關的。
- **逐字元延遲排除**:`char_delay_us` 沒有人設定,預設 0。
- **寫入實作**:單純的阻塞 `write()`,沒有 `tcdrain`。

改成記錄**每一次**超過 20ms 的卡頓(不只新高),得到分佈:

```
6 次 / 300 秒   全部 20-36ms   全部 60-61 位元組
```

**位元組數固定而卡頓在 20-36ms 之間跳,所以與資料量無關。**
60 位元組在 230400 baud 只要 2.6ms。量級是 **16ms USB 幀的 1-2 倍**,
指向 **macOS USB-serial 驅動的批次排程**,不是我們的程式碼。

先前那次 **215ms 是離群值,不是常態** —— 這一輪最大只有 36ms,
`cam_max` 142ms、`UNANSWERED` 1(今天最好的一輪)。

後三次卡頓相隔 71.7 / 60.0 / 64.9 秒,像有週期性,但**樣本太少,不下結論**。

**發生時機**:不是啟動殘留 —— 同一輪的卡頓落在 61 / 68 / 72 / 143 / 203 / 268 秒
(300 秒的 run),先前那個 215ms 的離群值在 171 秒,整段期間偶發。

**但「大約每 60-70 秒一次」不成立。** 同樣條件的下一輪(480 秒)
**一次都沒有**(`write max 18.49ms`,n=3200)。300 秒 6 次 vs 480 秒 0 次
—— 是零星的、run 間變異很大。那三個看起來規律的間隔只是三個樣本。

**這組數字的限制(重要,不要當產線數字用)**:
所有串列量測都是用 `spike.py` 跑的,而它**不載配方** ——
`insp split` 顯示 `inspect avg 0.00`,核心幾乎閒置。
傳輸本身不在乎檢驗負載,但**卡頓是否負載相依從未測過**,
全部樣本都來自一顆閒置的 core。要在有配方的負載下重量。

**另外**:那一輪沒有任何串列卡頓,`wait` 卻仍然 `max 174ms`。
所以**佇列等待的尾巴與串列卡頓無關**,是另一件事
(先前歸到「通知發出後沒被排到」,那條線也還沒收乾淨)。

### 適用範圍:這是 **macOS 開發機**的傳輸特性,不是出貨機器的

**目標機器是 Windows。** 上面所有數字都量在 Mac 的 USB-serial 驅動上,
而 20-36ms 正好是 16ms USB 幀的 1-2 倍 —— 那是 macOS 的批次排程行為。
**Windows 的驅動不同,必須在目標平台重量,不要把這些數字帶過去。**

嚴重性也不到 no-go:典型卡頓 20-36ms,對 plate 26000 的 396ms 預算,
而最好的一輪 `UNANSWERED` 只有 1。**先記著,之後在 Windows 上再看。**

若真要根治,方向是換傳輸(USB CDC 直連或網路)而不是調參數。

### 排除紀錄(不要重做這些)

尖峰原本是 `wait` 66-706ms,而 `idle_before > wait`(東西進佇列時執行緒已閒置)。
針對「交接」提出的五個假說,**每一個都有乾淨的量測,而每一個都無關**:

| 候選 | 判準 | 結果 |
|---|---|---|
| 積壓 | `depth_at_pop` 與 `idle_before` | depth 0-2,idle > wait → 不是積壓 |
| 鎖競爭 | 生產者 `push()` 耗時 | **max 0.050ms** → 鎖沒被搶 |
| 漏通知 | 讀 `TSQueue` | 正規 `condition_variable` + predicate |
| 排程優先權 | 提到 `QOS_CLASS_USER_INTERACTIVE` | 尖峰**沒有**消失(保留,但不是修法) |
| 儀器自己 | 計時 `LOGE` 本身 | 從未超過 20ms |

**真正的原因:`enq_us` 蓋在訊息「建構」時,不是「入佇列」時。**
中間隔著核心端配對(`perifPairFrameForReport`)與拆解記錄,全被算進
消費者看到的「佇列等待」。所以那五個假說**必然**全部失敗 ——
它們瞄準佇列之後,而時間花在佇列之前,東西那時還沒進去。

修正(在 `push` 前一行蓋章)後:`wait` avg 2.98-4.18ms -> **0.59ms**,
max 706-808ms -> **112ms**。

### 兩條方法上的教訓

**一、五個假說連續落空時,懷疑量測的邊界,不要找第六個假說。**
「wait」這個名字本身就是陷阱 —— 它讓人從不問起點在哪。

**二、一個數字看起來像證據,但可能什麼都分不出來。**
第一版只記了「記錄當下的 `qdepth`」,而積壓與沒被喚醒**都會**給出 qdepth 0。
要分開它們需要兩個數字:**取出當下**的深度,加上**執行緒閒置多久**。
同樣地,`write` 一個數字分不開「等鎖」與「上線」,拆開才看得到是線本身。

### 為什麼持續的滑移在真實料件上不可能(結構性論證)

**真實間距是隨機的,所以平移過的配對無法持續對齊** ——
殘差會立刻爆開並被視窗拒絕。那次 -3 的 `delta_max` 只有 217us,
表示時間戳側**始終是準的**,錯的只有核心的 tid 記帳,
而不規則的間距會把它沖掉。

**只有完美間距的虛擬物件才撐得住一個持續的滑移。**
這與「規則圖樣會藏住等於其週期的滑移」是同一條原理的兩面:
**間距的隨機性本身就是防滑移的機制**,而幻影測試因為間距規則,
反而是唯一需要擔心這件事的場合。

## 附錄:曝光參考點 —— 由接線解決,不需要時間戳(2026-08-09)

原本的擔心(合理):相機的觸發計數是對的,但若曝光被延後,影像裡可能是
**另外一顆**,而每一個時間戳仍然吻合、殘差看不出任何異常。

用背光當探針去量曝光視窗時,發現了更根本的事實:

```
light_duration    0us  ->  0 幀        <- 沒有光就沒有觸發
light_duration  100us  ->  亮度 158
light_duration  300us  ->  亮度 255（飽和）
```

**觸發就是背光脈衝本身**(觸發線騎在背光線上)。所以光與觸發是同一個邊緣,
`light_delay` 移動的是**兩者一起**,相對時序在硬體上是固定的 ——
這也是為什麼掃描 `light_delay` 時亮度全程不變。

### 結論:那個失效模式無法產生一張看起來正常的影像

場景只在觸發那一瞬間被照亮。若相機把曝光延後(例如推遲一個讀出週期),
那時背光已經熄滅 —— 得到的是**一張全黑的影像**,不是隔壁那顆的影像。
全黑會走 NA / 檢驗失敗,**不會變成一個錯誤的判定**。

**閃燈式背光與觸發同源,本身就是這個失效模式的防護。**

### 這個保證的前提(改動時要重新檢視)

- 照明必須是**閃燈**且與觸發同源。若改成**常亮背光**,這條保證立刻消失,
  延後的曝光就會拍到清晰的、錯誤的那一顆。
- 曝光時間必須不遠大於光脈衝。目前相機曝光 1000us、光 300us 即飽和。

工具:`tools/expose_window.py`(掃 `light_delay`,量亮度)。
它現在會在**沒有對比**時明講「無法下任何結論」—— 第一版在全黑的掃描上
用「> 50% 峰值」算出了「曝光視窗 0..1560us」,一個從零訊號算出來的自信答案。

## 產能調校流程(WebUI 精靈的規格,2026-08-09)

### 先修正一個不變量

C-1 的護欄寫的是 `2 x TOL <= min_detect_sep`(強制間距,保證視窗內只有一個候選)。
**但錯置真正需要的條件是:時間戳誤差 > 物件間距的一半** —— 配對取最近的那一顆。

**[驗]** 代入實測:

```
殘差       99.97% 落在 32-64us，最大 217us
物件間距   195mm / 503mm/s = 388ms
錯置門檻   間距的一半 = 194ms
餘裕       194ms / 0.064ms ~ 3000 倍
```

再加上**間距是隨機的**,所以持續性的滑移無法維持(見 slip 那一節)。
那條間距護欄防的,是一個已被殘差分佈排除三千倍的失效模式。

**[驗] A/B(同為 20 rpm,187 秒):**

```
                     edges/圈  accept/圈   rate拒絕  agree/disagree  delta_max
sep 28571 / win 5000   3.60      0.79        62        0 / 41        148us
sep  2000 / win  500   4.77      2.94         0      169 /  0        143us
```

吞吐 **3.7 倍**,間距拒絕歸零,而**配對變好**(拒絕變少 -> tid 序列不再被跳號打亂),
殘差分佈**完全沒變** —— 視窗不影響殘差,它只決定「多大的殘差還算數」。

### 精靈該依序決定的東西(順序是有相依的)

1. **相機 ROI + 曝光** —— 決定檢驗時間與電子延遲的分佈。
   有配方時 `inspect` 約 9.8ms,無配方是 2ms(那是「不檢驗」的成本)。
2. **量殘差分佈**(`cam_sync.delta_hist`,不是 `delta_max`)。
   視窗要蓋住**合法發生的最壞殘差**,建議取實測尾巴的 3-5 倍。
3. **設 `min_detect_sep` 再設 `match_window_us`** —— 裝置會把視窗夾到 `sep/2`,
   而工具印的是**請求值**。設完一定要讀回 `cam_sync.window_us` 確認。
4. **量電子延遲的尾巴**(`report_latency.cam_max_us`,**不是** `avg_us`,
   後者從閘門起算、含料件走路)。盤速上限來自
   `CAM->SWITCH = (29900-9315)/(2 x plate_freq)` 必須大於尾巴並留餘裕。
   **[驗]** 尾巴 368ms -> 40rpm(預算 257ms)必定停機;26rpm(396ms)才有餘裕。
5. **剩下的才是進料密度** —— 今天量到 4.7 顆/圈,26rpm 時約 2 顆/秒。
   到這一步之後,吞吐是震動盤/導槽的問題,不是控制的問題。

### 精靈必須避開的陷阱(每一個今天都踩過)

- **視窗要分兩階段**:獲取(校準)期偏移未知,窄視窗會讓校準**根本不收斂**
  (500us -> `CAMSYNC CAL FAILED`)。用生產視窗校準,**收斂後**才縮窄。
- **必須等到 READY(101) 才縮窄**。在 SPINUP(103) 縮窄會讓機器卡在那裡,
  閘門看得到 edges 卻一顆都不收。
- **檢驗進行中不可改盤速**。在途物件是用舊速度的 tick 幾何登記的,
  一改就對不上,`err 1` 停機。要停 -> 改 -> 再啟動。
- **未知鍵靜默忽略但回 `ack: true`**。每個設定都要讀回值確認,
  不能相信 ack(WebUI 的平鍵問題正是這樣藏了很久)。
- **判定全 NA = 沒載配方**,此時任何延遲/配對數字都不算數。

### 精靈的輸出

一組 `(ROI, 曝光, window, min_detect_sep, plate_freq)`,以及**它們各自的餘裕**:
殘差對視窗、尾巴對預算、間距對視窗。使用者要看得到自己離哪一道牆最近 ——
今天每一次「速度上不來」都是撞到不同的牆,而畫面上看起來完全一樣。

**不是編碼的問題**:bench 顯示 5MP 灰階 11ms,我們這張 0.25MP 約 **0.5ms**。
問題是 **1MB / 200ms = 5MB/s**,而預設走的是 raw RGBA
(`DataView_JPEG_quality = 0`,為了 WebUI 相容而留)。

### 管線稽核(已全部改為非阻塞)

```
inspQueue(10)        push_blocking       -> 丟最舊 + 計數
datViewQueue(10)     push_blocking       -> 丟最舊 + 計數
inspSnapQueue(5)     push                -> 本來就對
perifSendQueue(256)  push + 丟最舊        -> 本來就對
resPool(30)          fetchResrc_blocking -> 取不到就丟這幀 + 計數
```

原則:**丟一顆 = 它沒有判定 -> 噴嘴不動作 -> 回流(安全);
阻塞 = 它後面每一顆都遲到。** 四個丟棄計數器都保留,因為
**無聲丟棄與無聲停滯從外面看一模一樣,而兩者要的修法相反。**

**[驗]** 後兩項在目前負載下不是作用中的限制(92.4 -> 88.0),但仍該改。

## 五、新增的儀器

- **`yield` 漏斗**(在 `get_running_stat`):每一關的進/出/百分比/具名流失。
  第一次跑就同時指出「閘門只放行 24%,流失是間距」與「分選 0% = 沒載配方」。
- **`report_latency.cam_avg_us` / `cam_max_us`**:從**相機觸發**起算,
  可直接對 CAM->SWITCH 預算。`avg_us` 是從閘門起算、含料件走路,**不可拿來對預算**。
- **`virt_pulse`**:位置域(tick)的虛擬物件列車,抖動預設為週期的 1/10。
  **驗證未通過**,見下。

## 六、Caveats(新增)

### 注入不完整的訊息會弄壞核心 —— 今天三次

- 缺 `imgsrc` 的 `!fi` -> **SIGSEGV**
- payload 不符的 `!sc` -> **SIGSEGV**
- 只帶一個欄位的 `!st` -> 走到無條件執行的 `downSampSetup(*camera,*json)`,
  用空設定動相機,**判定歸零**(兩次,兩次的延遲數字都作廢)

這三個指向同一件事:**核心對不完整的訊息沒有防護**,而那正是 WebUI 送什麼
就吃什麼的路徑。

### 操作限制(每一個都是踩出來的)

- **檢驗進行中不可改設定**(盤速、閘門、相機)。在途物件是用舊的 tick 幾何
  登記的,一改就對不上 -> `err 1` 停機。必須 **退出 -> 改 -> 進入**。
- **視窗要分兩階段**:獲取(校準)期偏移未知,窄視窗會讓校準**根本不收斂**
  (500us -> `CAMSYNC CAL FAILED`)。用生產視窗校準,收斂後才縮窄。
- **縮窄前必須等到 READY(101)**。在 SPINUP(103) 縮窄會讓機器卡在那裡,
  閘門看得到 edges 卻一顆都不收。
- **週邊控制台只接受一個客戶端**,第二個連線會踢掉第一個 —— 兩個腳本同時跑
  會互相打斷,而症狀是「裝置不回應」。

### `virt_pulse` 未通過驗證

每圈的數量應與盤速無關(period 4000、一圈 120000 ticks -> 應為 30/圈),
實測是 4.59 與 1.66;嘗試次數也超過排程應有的量,88-97% 被閘門拒絕。
**所以量到的是閘門行為,不是注入器的排程。先別當治具用。**

### 漏斗的 >100%

短窗口(60s)下 `verdict` 曾出現 106% —— 分子分母的取樣時點不齊
(在途物件會讓判定數超過同期的接受數)。長窗口會稀釋掉而看不見。
**這個 bug 是縮短窗口才暴露的**,尚未修。

### 殘差沒有樣本

有兩次組態下 `delta_hist` 全零、`agree`/`disagree` 都是 0,而判定照常產生 ——
**時間戳配對那條路沒有被走到**。這是整套安全論證的證據來源,**未查明**。

# 2026-08-10 凌晨:含影像輸出的整體 profile

問題:**開著影像輸出時,整條管線的時間花在哪裡?哪一段在關鍵路徑上?**

四個條件,除了預覽以外完全相同,各 60 秒,20000 (plate freq)、真實料件、
`fi_hold.mjs` 開生產用的 FI session:

```
                     cam_avg  cam_max   accept/60s   核心內部
off   FI,不訂閱串流    18.1ms   32.0ms      846       insp queue 0.05 / inspect 7.10
raw   FI + 原始 RGBA   17.7ms   53.3ms      841       insp queue 0.03 / inspect 6.67
jpeg  FI + JPEG 85     18.1ms   33.7ms      845       insp queue 0.03 / inspect 7.02
quiet raw + 全靜音log  18.3ms  176.8ms      852       (見下)
```

`cam_avg_us` 是**相機觸發到板子處理完判定**,也就是關鍵路徑本身。

## 結論一:影像輸出已經不在關鍵路徑上了

平均 17.7 / 18.1 / 18.1 ms —— 三者的差距 0.4ms,小於條件之間的重跑誤差。
接受數 841/845/846 也一樣。**在佇列改成非阻塞之後,預覽對平均延遲與產能
都沒有可測量的影響**;8/09 記錄的 88ms vs 22ms 差距不復存在。

留下的只有尾巴:`cam_max` 32.0 (off) 對 53.3 (raw),約 +20ms,
而且只發生在預覽落後的那幾幀。

## 結論二:核心自己只佔 18ms 裡的 7ms,而且全在檢驗

一幀的核心內帳(raw 條件):

```
inspQueue 等待     0.03ms 平均 (最大 8.6)
檢驗本身           6.67ms 平均 (最大 37.5)   <- 核心唯一的大項
perifSendQueue 等  0.01ms 平均
serial write       0.02ms 平均
────────────────────────────────
核心合計           約 6.7ms
板子量到的總長     17.7ms
差額               約 11ms = 曝光 + 讀出 + USB + 板端處理
```

**這 11ms 這個行程量不到**,只能用減法得到 —— 但它現在是有名字的殘量,
不是「上游」。

## `insp split` 的 inspect 一直是 0.00 —— 儀器自己壞了

8/09 把 `enq_us` 的戳記移到 push 之前時,**沒有把讀它的統計區塊一起移**,
於是統計讀到的是初始值 0,`inspect` 印出 avg 0.00ms **且** max 0.00ms。
一個讀到零的計時器看起來像一段很快的階段,這是儀器出錯最貴的一種形式。
修正後同一台機器同一個設定,那一段是 **6.6-7.1ms**。

**規則:平均與最大同時為零的計時器,先懷疑儀器,不要當成結果。**

## 冗餘 log:每幀 26 行以上,一分鐘就把飛行記錄器蓋掉

ring 是 65534 槽,實測一次 60 秒的執行寫掉 **6.7 萬行**。
也就是說,**事故之後抓的 dump 已經不含事故**。

先量了它值不值得修:`INSP_LOG=warn` 把所有 LOGI 靜音(只剩一次比較,
不做格式化),延遲 18.0 -> 18.3ms、接受數 851 vs 852 —— **沒有差別**。
所以這是可讀性問題,不是效能問題,修法就該是**變稀疏而不是刪掉**。

`LOG_EVERY(n, ...)` 每個呼叫點保留 1/n(第一次一定印)。套用之後:

```
每幀行數     26+  ->  0.26
同樣 60 秒   67000 行  ->  233 行
延遲/產能    17.6ms / accept 850  (不變)
```

刪掉的是純位置標記(`====`、`>>>>`、`New frame go ...`),
變稀疏的是有數字但每幀重複的(frameInterval、clean_region、img transfer、
waterLvL、`[perif] report`、`[shape] matches`)。

**`DO INSP>> waterLvL` 本來是 LOGE**,所以連 WARN 過濾都關不掉它 ——
每幀印一次佇列深度。深度只有在**不是零**的時候才有意義,而那時丟棄計數器
本來就會叫。

## 順手挖出來的兩個缺陷

### `!sc` 沒有 `type` 就 SIGSEGV —— 根因找到了

`SC` handler 只有第一個比較檢查 NULL:

```c
char *cmd_type = JFetch_STRING(json, "type");
if (cmd_type && strcmp(cmd_type, "log_dump") == 0) { ... }
...
if (strcmp(cmd_type, "files_existance_check") == 0)   // <- 沒檢查
```

而 8/09 三次「注入弄壞核心」裡的 `!sc`,送的是
`{"target":"camera_setting_refresh", ...}` —— 這個指令**屬於 `RC`,不是 `SC`**。
送錯 handler 應該得到「不認識的指令」,不該是死掉。

**連帶影響:所有先前用 `!sc` 做「相機設定 refresh」的執行,那一行都是在殺核心。**

### 每一顆都是 NA,原因不是站別區域

以為是 `inspection_region` 左緣切到料件(區域 x=1380,配對中心 p50=1352)。
實際 log 說的是另一件事:

```
verdict NA: labeledData EMPTY (shape_based raw-gray path?) -- located but unjudgeable
clean_regions dirty -> part status ...
```

**兩個獨立的 NA 來源,而且每幀都發生**(所以 `sort` 那關是 0%,
`overall_pct` 0)。定位是成功的,判定不成立。**未解**。

## Caveats

- 上表的 `inspect 6.7ms` 是在**每顆都 NA** 的狀態下量的。定位與比對有跑
  (log 有 `[shape] matches`),但判定那段短路了 —— 真正判定得出結果時
  只會更長,**不會更短**。
- `quiet` 那一列的 `cam_max` 176.8ms 與 `insp queue max` 100ms 是單一次
  打嗝,與靜音無關(平均沒動)。**單一最大值不要當成趨勢。**
- 一次 `jpeg` 執行以 state=112 停機收場(gate loss `unstable`、n=19),
  已重跑;**halted 的那次數據作廢,不在表內**。
- `dview split` 的 `wait` 現在不是阻塞,是**預覽落後多久**。
  它會到 100-270ms,而同一時間關鍵路徑不動 —— 這正是非阻塞要的效果。
- 影像其實**只送三分之一**:1100 幀裡 750 幀因為 FPS 上限被跳過
  (`skipped img:750 of n:1100`)。所以上表的 raw/jpeg 成本是
  **10 fps 的預覽**,不是 30 fps 的。

## 把編碼故意變慢:預覽真的不影響判定嗎?

三個點差一兩毫秒不足以證明什麼,所以加了一個旋鈕:
`INSP_PERIF_FAULT_DVIEW_SLEEP_MS=<n>`,每幀在影像送出前墊 n 毫秒。

**[驗]** 同樣 60 秒、20000、原始 RGBA:

```
                      cam_avg   accept   agree/disagree   datView 丟棄
sleep 50ms             17.6ms     844        840 / 0           0
sleep 200ms            18.1ms     853        849 / 0           0
sleep 500ms(修正前)   19.2ms     657          0 / 647          0    <-- 壞掉
sleep 500ms(修正後)   18.3ms     849        843 / 0          151
```

500ms 那一列在修正前是**整台機器退化**:接受從 853 掉到 657(-23%),
出現 SKIP,而且 `agree` 歸零、`disagree` 647 —— 時間戳與序數兩套配對
完全對不上。

### 原因:佇列滿的時候丟掉的是「最新」的那幀

```c
if (datViewQueue.size() == datViewQueue.capacity())
{
    // 滿了 -> 把「正要進來」的這幀回收掉
    bpg_pi.resPool.retResrc(imgPipe);
}
else { ... 這裡才是丟最舊的程式碼 ... }
```

前面這個判斷讓後面「丟最舊」**永遠走不到 —— 是死碼**。所以負載一上來:

- 預覽播的是十幀前的佇列在慢慢排乾,**每一幀新的都被擋在門外**,
  畫面延遲整個佇列的長度而且永遠追不回來;
- `datViewDropCount` 全程是 0,**看起來像沒有丟過任何東西**。

改成無條件 push、滿了就淘汰最舊的之後,同樣的 500ms 停頓:
接受回到 849、`agree` 843 / `disagree` 0、丟棄計數器終於開始動(151)。

**`disagree` 647 是這套設計在正常運作**:幀被丟掉會讓序數配對錯位,
時間戳配對不會 —— 兩者不合就是有東西被丟了。它不是壞掉的證據,
是**偵測器叫了**。但在那個組態下機器確實少收了 23% 的料。

### 回答:編碼變慢會不會拖到給 uInsp 的時間

**不會拖延,但會丟。** 判定走 `perifSendQueue`,預覽走 `datViewQueue`,
兩條各自非阻塞,判定在預覽之前就已經入列;所以 sleep 從 0 加到 500ms,
`cam_avg` 只從 17.7 走到 18.3ms(在雜訊裡)。

真正的風險是**資源池**:預覽握著 image_pipe 緩衝區不放,池被抽乾時
取像端會丟幀(`poolEmptyDropCount`),而丟掉的那顆沒有判定。
這次沒踩到(池 30 格、預覽佇列 10 格,全程 dropPool=0),
但這是「更大張的圖 / 更慢的主機」會先撞上的牆,不是延遲。
