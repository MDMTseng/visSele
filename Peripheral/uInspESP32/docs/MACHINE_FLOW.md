# 全檢機:流程、憲法、與每一段的量測目標

這份文件存在的理由很具體:**同一組時間戳的參考點,在 2026-08-08~09 這一天被
重新推導了至少三次**,其中一次還被當成回歸故障追了一小時。每次 session 壓縮
之後,「`report_latency` 是從哪裡量到哪裡」這種事就得從程式碼重新讀一遍。

所以這裡記的不是結論,是**參考點與量測目標**:每一段是什麼、用哪個時鐘、
哪個計數器在看它、那個計數器**看不到什麼**、以及什麼情況下那次量測是廢的。

數字一律標記 **[驗]**(有量測支撐)或 **[推]**(從程式碼推導,未量測)。
不要引用沒有標記的數字。

---

## 一、物理流程

```
震動盤 ──> 轉盤 ──> 閘門感測器 ──> 相機 ──> 噴料站(SEL1/2/3) ──> 排出 ──> 回流
                     ^gate_pulse    ^CAM1_on        ^SWITCH / SEL*_on
                     tick 0         +654            +29900 / +30000..31520
```

**回流不是報廢。** 噴口不動作 = 料件回到震動盤重跑一圈。只有「在某一圈裡
把判定發給錯的物件」才會出貨壞品 —— 這是整套設計的安全邊界,也是為什麼
「停機而不猜」永遠優於「猜一個」。

**tick 率 = `2 x plate_freq`** —— **[驗]**,V-31 已解(2026-08-09)。

驗法:量「閘門->相機」的行程時間,對照 NVS 裡的 `CAM1_on`。

```
plate  5000  travel 915.6ms   9315/(2f) 預測 931.5ms   1.7%
plate 10000  travel 462.2ms             預測 465.8ms   0.8%
plate 20000  travel 231.5ms             預測 232.9ms   0.6%
```

**重要**:`CAM1_on` 的**實際值是 9315(NVS)**,不是原始碼裡的預設 654。
拿編譯預設去推導會差 14 倍 —— 這個錯今天犯過一次。
**要看偏移一律 `get_setup`,不要讀原始碼。**

由此,預算可以標 **[驗]**:

```
CAM->SWITCH = (29900 - 9315) / (2 x plate_freq)
  plate 10000 -> 1029 ms
  plate 26000 ->  396 ms
```

## 二、憲法(只有兩條)

**C-1 配對是證據性的,不是序數性的。**
判定屬於哪一顆,由「報告攜帶的相機時間戳」與「該物件的相機觸發時刻」比對決定,
不靠計數、不靠順序。護欄是 `2 x TOL_US <= min_detect_sep_us`
—— 視窗內只能有一個候選,唯一性由間距保證。

**C-1a** 維護是循環的:`gate()` 從**每一份通過視窗的報告**重新量測 `offset_us`
(最後一行是整個覆寫,不是混合)。安全性來自唯一性,不是來自教師的正確性。

**C-1b** 連續 `LOST_N` 份報告的最近物件落在視窗外 → `CAM_CLOCK_LOST` 停機。
**停機是設計行為**,不是故障。

**C-2 取景是幾何性的。** 相機在 `CAM1_on` 觸發,由 tick 計數決定,與報告無關。

其餘一切(節流、skip 政策、auto_rate、重新校準時機)都是**運作層**,
可以改、可以關,不影響上面兩條。

## 三、時鐘與參考點(**最常被搞混的部分**)

| 名稱 | 誰蓋的 | 蓋在什麼時刻 | 用途 |
|---|---|---|---|
| `trig_us` | 板子 `newPulseEvent` | **閘門偵測到料件** | `report_latency` 的起點 |
| `cam_us` | 板子 CAM ISR | **相機觸發脈衝發出** | 配對的基準(64 位元) |
| `cam_ts` | 相機硬體 | 相機自己的時鐘 | 報告攜帶,與 `cam_us` 比對 |
| `host_rx_us` | 核心 | 影像推進 `inspQueue` | 核心端拆解 |
| `host_insp_us` | 核心 | 進入 `ImgPipeProcessCenter_imp` | 核心端拆解 |
| `enq_us` | 核心 | 報告推進 `perifSendQueue` | 核心端拆解 |

**`report_latency.avg_us` = `trig_us` -> 報告被處理 = 閘門 -> 判定**,
含料件走路。韌體的欄位註解自己寫著 `for the gate->report latency stat`。
**拿它對 CAM->SWITCH 預算是比錯區段**,這個錯誤在同一天犯了兩次。

**要用的是 `report_latency.cam_avg_us` / `cam_max_us`**(2026-08-09 新增),
從 `cam_us` 起算 = **相機觸發 -> 判定 = 電子延遲**,與預算同一個起點。

**[驗]** 三個盤速下的拆解:

```
plate  5000   gate->rep 929.6ms | cam->rep 14.1ms | travel 915.6ms
plate 10000   gate->rep 475.9ms | cam->rep 13.7ms | travel 462.2ms
plate 20000   gate->rep 245.7ms | cam->rep 14.2ms | travel 231.5ms
```

**電子延遲不隨盤速變化(14ms),行程時間完美反比。**
`cam_max_us` 是 253-259ms —— 對 plate 26000 的 396ms 預算,
**最壞的一份報告用掉 65%**。限制吞吐的是尾巴,不是平均。

## 四、每一段的量測目標,以及它看不到什麼

### 閘門
- `gate.accept` / `edges`:收下的 / 感測器邊緣總數。
- 拒絕分四格:`rej_rate`(節流)、`rej_width`(脈寬)、`rej_unstable`(轉速不穩)、
  `rej_dist`(距離)。**合成一格會互相掩蓋** —— 這是拆開的原因。
- **看不到**:被相機拒絕的觸發。相機在過觸發時是**丟棄**而非排隊
  (**[驗]** 200 發 400Hz → 94 幀,frame_id 連續無跳號),所以那些觸發不留痕跡。
  相機自己數得到:`FrameSpecInfo` 的 `ExtTriggerCount`(偏移 4,32-bit LE)。

### 相機 / 取像
- `cam_sync.sync_pulses` / `learned` / `cal_runs` / `cal_fails`。
- **看不到**:`AcquisitionStart` 失敗。核心會 `LOGE` 一筆然後**照常運行**,
  板子端看到的是「打脈衝、零報告、最後 `CAM_CLOCK_CAL_FAILED`」,
  與時鐘故障**無法區分**。這一天有兩次一小時等級的誤診來自這個沉默。

### 檢驗
- 核心端 `insp split`:`queue`(等待被檢驗)/ `inspect`(運算本身)。
- **[驗]** 有配方(10155,工位 318x424)時 `inspect avg 9.78ms / max 96.19ms`。
- **[驗]** 沒有配方時 `inspect avg 2.02ms` —— 那是「不檢驗」的成本。
  **沒載配方的延遲量測缺了最大的一塊,不要當產線數字用。**
  判準:`count` 全是 `NA` 就是沒載配方。

### 報告送出
- `perif write`:`write`(串列寫入)與 `wait`(佇列等待)**分開**。
  合成一個數字時兩者會互相掩蓋 —— 平均由前段主導,尾巴由後段主導。
- **[驗]** `write avg 0.47ms / max 158ms`;`wait avg 2.98ms / max 808ms`,`qdepth 0`。
  `qdepth` 是 0 卻等 808ms → **是送出執行緒被餓死,不是積壓。**

### 配對
- `agree` / `disagree` + `CAMSYNC MISMATCH tid=.. ts_tid=.. d=..` 明細。
  **偏移量比次數有用** —— 常數偏移與雜訊是完全不同的病。
- `delta_hist`(log2 分桶)比 `delta_max` 有用:視窗要蓋住**合法發生的最壞殘差**,
  而 max 分不出「一顆離群」與「經常接近」。
- **[驗]** 有配方時 `disagree 0 / agree 2866 / delta_max 163us`。
- **存疑**:無配方時同盤速量到 100% 分歧、常數偏移 +2,並曾寫成
  「序數配對落後在途報告數」。**有配方時是 0**,所以那個結論可能是無配方狀態的
  產物。在有配方下重跑盤速掃描之前不要引用。

### 噴料
- `count`:`SEL1/2/3` / `NA` / `UNANSWERED` / `SKIP`。
- `UNANSWERED` = 物件到 SWITCH 時還沒有判定(`err 2 OBJECT_HAS_NO_INSP_RESULT`)。
- **看不到**:`report_latency` **只在報告到達時累加**,所以太晚到或沒到的
  那些**不在統計裡**。avg/max 是倖存者的分佈,而害死機器的正是缺席的那條尾巴。

## 五、什麼情況下這次量測是廢的(逐項檢查)

這一天有五次「量到空的」,每一次看起來都像可靠證據:失敗可重現、症狀一致。

1. **沒載配方** → 判定全 `NA`,檢驗成本缺席。查 `count`。
2. **沒送 `stepper_enable` 或盤速 0** → `sync_pulses=0`,校準必敗。查 `pulses`。
3. **沒設 `INSP_PERIF_VERDICT_PATTERN`** → 判定全是 NA(65535),
   「零錯置」這個通過條件**不可能失敗**。`jitter_sweep` / `regress_watch` 需要它;
   `soak_real` **絕不能**有它(它要真實判定)。
4. **孤兒 core** → 舊的 core 仍持有相機與序列埠,新的拿不到影像。
   開跑前數一次 `pgrep -f mac-arm64/visSele`。
5. **相機不出圖** → `AcquisitionStart` 回 `USB3Vision write_memory error`,
   而列舉與設定都正常。`DeviceReset` 每次都救得回來(**[驗]** 五次),
   但**要在沒有 core 持有裝置時才問得到**。
6. **視窗被夾** → `match_window_us` 會被夾到 `min_detect_sep_us/2`,
   而工具印的是它**請求**的值。掃視窗時 `min_detect_sep_us` 必須同步放大。
7. **一顆種子跑一整排** → 掃描的各列不獨立時,量到的是同一個事件的多份複本,
   而且**在最沒有資訊量時看起來最紮實**(各列高度一致)。

## 六、開著的問題

- **端到端的組成:已確認是行程,不是電子延遲。** **[驗]**
  盤速 5000 / 10000 / 20000 -> 924 / 479 / 276 ms,**隨盤速反比變化**。
  固定的電子延遲不會這樣縮。核心端只佔約 13ms(inspect+queue+wait+write),
  其餘是料件從閘門走到相機。
  (量測注意:兩段之間沒有 `reset_running_stat`,第二段是累計值,
  276ms 是減回去算的 —— 掃描前先重置。)

  **但 tick 換算對不上**:`CAM1_on=654`,若 tick 率是 `2 x plate_freq`,
  盤速 10000 應該只有 33ms,而實測是 479ms(約 4700 tick-等效)。
  這正是 **V-31** 那個 2 倍量綱歧義的實際後果 —— 在它解決之前,
  **任何用 tick 換算出來的時間都不要當 [驗] 用**,包括 CAM->SWITCH 的預算。
- **送出執行緒的喚醒延遲**(原記為「餓死」)。**[驗]** 已定位到一側:

```
WAIT SPIKE  82.9ms: idle_before 206.6ms, depth_at_pop 0 -> 執行緒 IDLE
WAIT SPIKE 148.0ms: idle_before 282.7ms, depth_at_pop 1 -> 執行緒 IDLE
```

  `idle_before > wait`,表示東西進佇列時執行緒**已經在閒置**。所以不是積壓。
  `TSQueue` 用的是正規 `condition_variable` + `notify`,所以也不是漏通知。
  而 `wait` 的定義就是 push -> pop,在佇列空、執行緒閒置時它**就等於
  notify -> 執行緒真正被排到**的時間。

  **剩下的候選只有兩個:OS 排程延遲,或 `mutex_` 被長時間持有。**
  下一刀:在 `push` 內 notify 前後各蓋一個時間戳,把「通知本身」與
  「被排到」分開。

  影響目前有界:`cam_max_us` 187-259ms,對 plate 20000 的 514ms 預算
  仍有餘裕,但對 26000 的 396ms 只剩 35%。**這是提吞吐的門檻。**
- **配對偏移結論存疑**(見上)。
- **WebUI 無法設定機器**:`SETTABLE_KEYS`(`src/script.jsx:1555`)全是平鍵,
  裝置只收群組,而裝置對未知鍵**靜默忽略但回 ack true**。
  畫面症狀:按下啟動後出現「轉速沒有寫進裝置,未進入檢測模式」。
- **曝光參考點**:`cam_ts` 指的是觸發到達還是曝光開始?前者的話,殘差對
  「照到哪一顆」一無所知,得靠外部光感測器才問得到。
- ~~**V-31**:`pulses_per_rev` 的 2 倍量綱歧義。~~ **已解**(見第一節)。
