# 5 MP live view:量測與結論

2026-08-23

問題:取消 ROI crop,直接串 2448×2048 全幅畫面。用什麼線路格式、什麼渲染
路徑?

全部數字都在**真正的 Electron 31 / Chromium 126** 裡量,GPU 是 Intel UHD 620
(和 Surface Go 3 同級),素材是這台相機的真實灰階畫面
(`InspectionCore/Core0_1/data/BMP_carousel_test`)。

工具:`UI/Launcher/tools/stream_lab/`。

---

## 0. 兩個把早期結論帶偏的量測錯誤

寫在最前面,因為它們各自都足以讓人做出相反的決定。

**合成影像的壓縮率是假的。** 我一開始用程式畫的背光圖 q85 只有 93 KB;真實
畫面同樣 q85 是 **422 KB**,4.5 倍。任何以合成圖推導的頻寬結論都不能用。

**`<img>.decode()` 的 1 ms 是快取命中。** 重複使用同一個 blob URL 時瀏覽器
不會重新解碼。每幀換一個新的 URL 之後是 **36 ms**。live stream 不會送兩次
同一幀,所以測試也不能。

還有一個量錯的指標:「主執行緒忙碌時間」我原本量的是處理一幀的**牆鐘時間**,
而 `await` 期間主執行緒是空的。改用 4 ms 心跳量真正的阻塞之後,所有路徑都是
p50 0.00 / p95 1.5 ms —— 因為 **`ImageDecoder` 本來就在別的執行緒解碼**。
這也解釋了為什麼把解碼搬進 Worker 沒有任何好處(18.2 vs 18.1 ms)。

---

## 1. 現況做不到

要求 20 fps,`createImageBitmap` → 2D canvas:

```
rendered 12.0 fps   dropped 47/120   end-to-end p95 465 ms
```

只渲染一半的幀,而且畫面落後將近半秒。**不管選哪種線路格式,這條路都得換。**

---

## 2. 路徑比較(20 fps,JPEG q85 422 KB)

| pipeline | fps | 掉幀 | e2e p95 | CPU |
|---|---|---|---|---|
| `createImageBitmap` → 2D(現況) | 12.0 | 47/120 | 465 ms | — |
| `ImageDecoder` → 2D | 17.8 | 14/120 | 41 ms | — |
| `ImageDecoder` → WebGL | 20.2 | 0 | 33 ms | 6.5% |
| Worker `ImageDecoder` → WebGL | 20.2 | 0 | 20 ms | — |
| raw(4.8 MB)→ WebGL | 20.1 | 0 | **91 ms** | 6.4% |

**raw 沒有贏。** CPU 一樣,延遲三倍,頻寬 11 倍。原因很物理:4.8 MB 在
350 MB/s 的通道上光是送就要 14 ms,而且是序列化的。速率拉高之後 raw 從不掉幀
但延遲一路惡化到 296 ms(60 fps)—— 它不是跟上了,是把落後藏在佇列裡。

---

## 3. 兩個把上限推高的改動

### 3.1 只上傳 Y 平面

解碼出來的 `VideoFrame` 是 **I420**,不是 RGBA:Y 平面 4.8 MB,U/V 各
1.2 MB。而來源是灰階相機,U/V 是常數 128,不帶資訊。

原本 `texSubImage2D(..., gl.RGBA, ..., videoFrame)` 讓 Chromium 做 I420→RGBA
轉換再推 **20 MB** 進 GPU,為了一張資訊量 4.8 MB 的影像。

`copyTo()` 不能單獨選一個平面,所以 `decoderYGL` 複製全部 7.5 MB 但只上傳
Y 前綴。一次 7.5 MB 的 memcpy 約 1 ms,換回每幀 15 MB 的 GPU 流量。

也試過直接把 `VideoFrame` 用 `format=RED` 上傳(`decoderRedGL`)—— 不會報錯,
但也沒有比較快,轉換顯然照做。

### 3.2 並行度 2

`ImageDecoder` 在別的執行緒解碼,所以「一次只處理一幀」會讓主執行緒在解碼
期間空等。放行第二幀之後上限直接從 30 fps 跳到 60 fps。

代價是**順序**:兩個解碼可能反序完成,而 live view 把舊幀畫到新幀上比掉幀更
糟。所以繪製這一步用序號閘門 —— 比畫面上那張舊的幀會解完就丟掉,永不繪製。

並行度 3 沒有比 2 好,45 fps 時反而更差(e2e 300 ms,42 掉幀)。**2 就是答案。**

| fps | conc | rendered | 掉幀 | e2e p95 | CPU |
|---|---|---|---|---|---|
| 30 | 1 | 29.0 | 7 | 35 | 8.9% |
| 30 | **2** | **30.1** | **0** | **28** | 9.0% |
| 45 | 1 | 28.4 | 100 | 31 | 10.5% |
| 45 | **2** | **45.2** | **0** | 36 | 13.8% |
| 60 | 1 | 36.1 | 144 | 32 | 12.1% |
| 60 | **2** | **60.0** | 1 | **22** | 19.1% |
| 60 | 3 | 60.1 | 0 | 27 | 18.9% |

| q | KB/幀 | 頻寬 | 解碼牆鐘 | e2e p95 | CPU |

| 60 | 120 | 3.1 MB/s | 19.4 ms | 23–28 ms | 6.7% |

但三次 q60 都出現約 283 ms 的最大值,值得留意。

## 6. 結論與設定

**JPEG q75 → `ImageDecoder`(並行度 2)→ Y 平面 → R8 WebGL 上傳。**

```
5 MP · 30 fps · 0 掉幀 · 端到端 24 ms · UI 端 8.1% 的一顆核心 · 線路 6.9 MB/s
```

對照現況的 12 fps / 465 ms。

### 兩分鐘持續運轉

30 fps、q75、`decoderYGL`、並行度 2,連續 120 秒 3600 幀:

| | |
|---|---|
| 到達 / 渲染 | 3600 / 3509(掉 91,2.5%) |
| 端到端 | p50 **17 ms** · p95 23 ms · **max 326 ms** |
| 主執行緒阻塞 | p50 0 · p95 1.3 ms · **max 306 ms** |
| CPU(單核百分比) | p50 7.8%(Tab 6.5 · GPU 0.7 · Browser 0.3) |
| RSS | 起 684 MB → 終 **492 MB** · max 703 MB |

**沒有洩漏** —— 記憶體結束時比開始時還低,回收正常。但 703 MB 的峰值在 4 GB
的機器上要記著。

兩件要追的事:

1. **約 300 ms 的停頓。** `max` 那一欄三個數字同時出現(阻塞 306、e2e 326、
   到達間隔 320),所以是單一事件讓整條路一起卡住,120 秒內發生一兩次。最可能
   是大緩衝區的 GC。畫面上會看得到,但不致命。
2. **掉幀從 0 變成 2.5%。** 六秒的短跑是 0,持續運轉會累積。和上面那個停頓
   可能是同一件事。

### 真正的瓶頸換到核心端了

`jpeg_bench` 量到 5 MP gray q75 編碼 **12.08 ms/幀**:

| live view fps | 核心編碼 | UI | 合計(單核百分比) |
|---|---|---|---|
| 15 | 18% | 4% | 22% |
| 20 | 24% | 6% | 30% |
| 30 | 36% | 8% | 44% |

目標機是兩顆核心,而且要同時跑檢驗。**建議預設 15–20 fps,上限開到 30**,
用 `IMG_STREAMING_MAX_FPS` 那個 cap 控制。盤面本來就只有 23 件/秒,更高的
更新率不帶額外資訊。

要再往下壓核心端,順序是:live view 用 1/2 解析度而只在放大時取全解析
(編碼成本降 4 倍)→ Intel QSV 硬體編碼 → 最後才是換 codec。

## 7. 沒有走的路,以及為什麼

**raw 傳輸**:延遲更差(§2、§4),頻寬 11 倍,CPU 沒省。

**Worker 解碼**:`ImageDecoder` 已經不在主執行緒,搬進 Worker 沒有量得出來的
差別。

**shared memory / core 變 DLL**:主行程建的 `SharedArrayBuffer` 送到 renderer
會**靜默消失**(兩邊都沒有錯誤,handler 從未觸發)—— Node 和 Chromium 是不同
行程的不同 V8 isolate。唯一能真正零複製的做法是把原生模組載進 renderer,也就
是 `nodeIntegration:true` + `contextIsolation:false`。而零複製能省的只有每幀
約 0.6 ms 的非主執行緒 CPU(§ 量測:5 MB memcpy = 0.63 ms),代價是核心執行緒
跑進 Chromium 的排程裡、崩潰互相帶走、以及剛建好的監管/更新機制全部作廢。
不值得。

**`webContents.send` 傳像素**:75 MB/s,只有 WebSocket 的 350 MB/s 的五分之
一,尾端也更差。像素不要走 IPC。
